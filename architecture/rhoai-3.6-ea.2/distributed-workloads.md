## Purpose

**Short**: Validates distributed training and inference workload integrations on Red Hat OpenShift AI.

**Detailed**: This repository is an end-to-end test and example suite, not a long-running platform controller. It exercises Kubeflow Training Operator v1 PyTorchJobs, Kubeflow Trainer v2 TrainJobs and TrainingRuntimes, KubeRay RayClusters and RayJobs, Kueue admission and resource queues, and KServe ServingRuntime configuration. The shared Go support library creates namespaces and Kubernetes resources, obtains clients for the relevant APIs, waits for workload conditions, and captures logs and events for diagnostics.

The repository also supplies benchmark and example manifests, model/dataset/runtime images, and training scripts. Examples use MinIO for S3-compatible data exchange, optional NFS storage in the Kueue workshop, and a KServe TorchServe runtime for stable-diffusion. The test suite is intended to run against an installed ODH/RHOAI cluster with the distributed-workload components enabled; it does not itself reconcile those platform components.

## Architectural Analysis

The principal architectural boundary is between test orchestration and the cluster services under test. Go tests use typed Kubernetes clients and shared helpers to create isolated namespaces, queues, jobs, Ray resources, notebooks, and role bindings, then observe status and collect diagnostics. The `trainer` suite is the most actively developed path and validates Trainer v2 with JobSet/OpenMPI and Kueue; `kfto` covers the legacy PyTorchJob path; `odh` covers KubeRay; and `fms` checks foundation-model fine-tuning through both KFTO and Trainer v2.

The repository is also a catalog of deployable workload examples rather than one deployable artifact. Its manifests are deliberately heterogeneous: some examples run a single-replica MinIO deployment or stateful set, one workshop runs a privileged single-replica NFS server, and distributed training manifests consume cluster-scoped runtimes and queues supplied by Kubeflow/Kueue. This makes the repository useful for integration coverage but means example credentials, public routes, mutable image tags, and privileged workshop infrastructure must not be treated as production defaults.
