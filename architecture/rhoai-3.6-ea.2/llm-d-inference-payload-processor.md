## Purpose

**Short**: A pluggable gRPC External Processing service that inspects and mutates inference request and response payloads for an llm-d gateway.

**Detailed**: The Inference Payload Processor (IPP) runs beside an inference gateway proxy and receives request/response headers, bodies, and trailers through Envoy's External Processing API. Configured plugins can rewrite payloads, select profiles, extract model signals, and add routing headers so one gateway endpoint can front multiple models or inference pools.

The service is implemented as a Go binary managed by controller-runtime. It loads a `PayloadProcessorConfig`-shaped YAML document from a mounted ConfigMap, watches labeled ConfigMaps for base-model-to-adapter mappings, and exposes External Processor and health gRPC services. The model-selection and plugin framework depends on `llm-d-router`; observability is provided through Prometheus metrics and optional OpenTelemetry tracing.

## Architectural Analysis

IPP is a synchronous data-plane extension point: Envoy streams selected HTTP lifecycle events to the processor, and the processor returns mutations or immediate responses. The Helm chart makes event selection explicit and defaults all request/response headers, bodies, and trailers to be sent. In the Istio provider mode, an `EnvoyFilter` inserts the ext_proc filter into the configured Gateway and sets `failure_mode_allow: false`, making processor availability part of request success. The GKE mode instead creates a `GCPRoutingExtension` and gRPC health-check policy.

The processor is deployed once per gateway as a namespaced service by default. Configuration is represented by an API-shaped Go type but is normally embedded in a ConfigMap rather than submitted as a Kubernetes custom resource. The default chart uses a namespaced Role and ServiceAccount; enabling `multiNamespace` changes this to cluster-wide ConfigMap read/list/watch permissions, which broadens the configuration trust boundary.

The default image is a statically linked, non-root Go binary in a distroless runtime. This minimizes the runtime image but does not satisfy the documented dynamic-linking/OpenSSL requirements for the Konflux `check-payload` FIPS gate without downstream build changes. Runtime TLS is optional and, when enabled, uses a generated self-signed certificate; the Istio chart's DestinationRule currently sets `insecureSkipVerify: true`, so certificate authenticity is not verified on that path.
