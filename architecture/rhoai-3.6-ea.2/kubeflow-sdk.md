## Purpose

**Short**: A unified Python SDK for defining and running Kubeflow training, optimization, pipeline, Spark, and model-registry workloads through local or Kubernetes-backed clients.

**Detailed**: The package presents Pythonic APIs over several Kubeflow projects. The Trainer client supports Kubernetes, local-process, and Docker/Podman execution; Kubernetes mode loads kubeconfig or in-cluster credentials and uses the Kubernetes Python client to submit and inspect training resources. The SDK also exposes optional integrations for Kubeflow Pipelines, Katib-based optimization, Spark Connect, Model Registry, cloud checkpoint storage, and RHOAI training instrumentation.

The repository is consumed by user applications and test/e2e runners; it does not build or deploy a controller, service, or operator of its own. Its Kubernetes tenancy and authorization behavior therefore inherit from the caller's kubeconfig or service-account credentials and from the Kubeflow control planes. The only repository-local CRD is a namespaced `SparkConnect` definition under `hack/crds/`, supplied for Spark integration testing rather than reconciled by this package.

## Architectural Analysis

The SDK is a facade over multiple control-plane APIs with a backend abstraction at the Trainer and Spark boundaries. A caller can keep the same high-level training configuration while selecting a Kubernetes backend for production or a local process/container backend for development. The Kubernetes Trainer backend deliberately checks namespaced `TrainingRuntime` objects before falling back to cluster-scoped `ClusterTrainingRuntime` objects, giving namespace-local runtime definitions precedence while retaining shared defaults.

The package is primarily a client-side object translator and polling layer: it creates or reads resources through the Kubernetes Python client, reads control-plane metadata from a public ConfigMap, and turns runtime/job status into SDK types. Optional RHAI instrumentation generates code that is injected into user training processes for progression tracking and checkpoint handling. This makes the SDK useful across platform installations, but also means authentication, RBAC, network policy, quotas, and cross-tenant isolation are not enforced by the SDK itself.

The release checkout is Python-only and has a hash-pinned `requirements.txt` plus `uv.lock`, but its `uv` development overrides point at moving upstream `master` branches. There are no release/deployment manifests or Konflux build definitions in this checkout, so container/FIPS conclusions are limited to the source package and the non-Konflux Spark e2e Dockerfile.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Caller-provided kubeconfig/service account and Kubernetes RBAC | Kubernetes/platform | SDK has no per-tenant authorization layer; an over-privileged caller can access other namespaces or cluster-scoped resources. |
| Data storage | Namespaced Kubernetes objects; checkpoint data may use shared object storage | Kubernetes plus storage/application configuration | Object-storage tenant separation is external to the SDK; credential and URI mistakes can cross tenant boundaries. |
| Network traffic | No NetworkPolicy or AuthorizationPolicy in repository | Platform/operator | Network isolation is not established by the SDK. |
| Compute & resources | SDK passes requested node/resource settings to workload APIs | Kubeflow control plane/Kubernetes scheduler | No quotas, limits, or fairness policy are created here; starvation/isolation depends on cluster policy. |
| Configuration & secrets | Data-connection Secret is read by explicit name in the selected namespace; `HF_TOKEN` is runtime environment state | Kubernetes namespace/RBAC plus application | No Secret creation or rotation; users must prevent broad service-account access and avoid leaking tokens into generated jobs/logs. |
| API scoping | Namespaced list/get calls use `self.namespace`; runtime lookup additionally falls back to cluster-scoped runtimes | Kubernetes API plus SDK selection logic | Cluster-scoped fallback intentionally shares runtimes across namespaces; authorization and server-side policy remain external. |
