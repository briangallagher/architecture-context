## Purpose

**Short**: batch-gateway provides an OpenAI-compatible batch API that stores batch files and coordinates asynchronous inference work through llm-d gateways.

**Detailed**: The component exposes batch and file APIs through a Go HTTP server. It persists batch and file metadata in PostgreSQL, stores file content in an S3-compatible backend or filesystem implementation, and uses Redis/Valkey for exchange and queue state. Tenant identity is propagated from an HTTP header into request context and storage/database operations.

The repository builds three independently deployable containers: the API server, a batch processor, and a garbage collector. The processor consumes work and routes inference requests to configured llm-d inference gateways, while the garbage collector removes expired batches/files and watches Kubernetes resources where configured. All processes expose operational endpoints and support graceful shutdown and OpenTelemetry tracing.

## Architectural Analysis

The design separates synchronous API handling from asynchronous execution. The API server owns batch/file CRUD and uses shared client construction for PostgreSQL, Redis/Valkey, object storage, and inference services. The processor owns polling, dispatch, concurrency control, retries, and result persistence; the garbage collector provides lifecycle cleanup. This makes the data plane horizontally separable, but also makes the configured database, cache, object store, and inference gateway shared dependencies for the worker set.

Tenant isolation is implemented in application data paths rather than Kubernetes resources. Middleware extracts the configured tenant header (default `X-MaaS-Username`), handlers add tenant predicates to database queries, and S3 keys are prefixed by a tenant-derived folder. API routes have no local authentication enforcement, so the surrounding RHOAI ingress/authentication layer must establish and protect the tenant header. The absence of repository RBAC, Service, Route, NetworkPolicy, and workload manifests limits what can be concluded about that platform boundary.

Konflux Dockerfiles use dynamic CGO builds with `strictfipsruntime` and digest-pinned UBI images. Runtime TLS is configurable for the API server and outbound clients, with TLS 1.2 as the default minimum and system certificate verification unless explicitly overridden. The client code contains an insecure-verification switch intended for testing; operational configuration should keep it disabled.
