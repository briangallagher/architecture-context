## Purpose

**Short**: Cluster-scoped operator that uses an `AIGateway` resource to install and lifecycle-manage the RHOAI AI Gateway, including optional batch-gateway and Models as a Service bundles.

**Detailed**: The operator runs a controller-runtime manager and reconciles the singleton `AIGateway` custom resource. Its `batchGateway.managementState` and `modelsAsAService.managementState` fields select whether the corresponding manifest bundles are rendered and applied; both default to `Removed`. The CRD enforces the name `default-aigateway` and reports module, release, and sub-module readiness status.

The operator is a deployment orchestrator rather than the AI request data plane. It renders vendored kustomize bundles, substitutes image and namespace parameters, creates or updates their Kubernetes resources, and coordinates teardown and selector migration during upgrades. It also watches platform state and managed resources and exposes health and metrics endpoints for cluster operations.

## Architectural Analysis

This is a singleton, cluster-scoped control-plane module. A single `AIGateway` object drives two independently managed sub-modules: the llm-d batch gateway and MaaS. The operator delegates resource construction to the OpenDataHub operator action framework, while retaining module-specific decisions for platform namespaces, image substitutions, readiness aggregation, teardown handshakes, and stale Deployment selector migration.

The deployment boundary is deliberately broad: the operator needs to create/update workloads, RBAC, CRDs, Gateway API routes, monitoring objects, service accounts, secrets, and admission webhook configuration for the bundles it installs. This makes the service account a high-value cluster principal. The code mitigates some operational risks with fresh reads for ConfigMaps and Secrets, owner references on generated roles, UID/resource-version delete preconditions during selector migration, and explicit health/readiness conditions; the broad escalation RBAC remains an architectural risk.

The operator itself has no public ingress route. Its externally relevant network surfaces are the Kubernetes API connection, HTTP health probes on 8081, and the internal metrics Service on 8443. Metrics authentication and authorization are enabled when secure metrics are configured; the metrics certificate is supplied by the OpenShift service CA in the default OpenShift deployment.
