## Purpose

**Short**: A reverse proxy that coordinates disaggregated LLM prefill and decode requests between a prefill worker and a local vLLM decoder.

**Detailed**: The sidecar listens on a configurable port (8000 by default) and exposes OpenAI-compatible completion endpoints. Requests without a prefill target are passed directly to the decoder at `localhost:8001` by default. Requests carrying `x-prefiller-host-port` (or the deprecated `x-prefiller-url`) are sent through the selected P/D connector, allowing the prefiller to establish KV-transfer state before the request is forwarded to the decoder.

The proxy supports NIXL v2 (the default), legacy NIXL v1, and LMCache connectors. It can serve TLS with a supplied certificate or a generated self-signed certificate. Optional SSRF protection watches one namespace-scoped `InferencePool` and matching Pods, then rejects prefill targets whose host is not on the resulting allowlist. The repository is deprecated; its implementation moved to `llm-d-inference-scheduler` under `cmd/pd_sidecar` and `pkg/sidecar` (README.md:3-9).

## Architectural Analysis

This is a single-process Go reverse proxy deployed as a one-replica StatefulSet. Its request path is intentionally data-plane oriented: the proxy terminates or accepts client traffic, optionally performs a prefill exchange, and then forwards to a decoder. The prefiller destination is request-selected through a header, while the decoder target is constructed from a local host and configured port. A small LRU cache retains prefiller proxy handlers.

The optional allowlist is the principal Kubernetes integration. When enabled, the process uses `client-go` dynamic APIs and informers to watch a named `InferencePool` and Pods selected by that pool in one namespace. The allowlist is host-based rather than port-based, so every port on an allowed host is accepted. This provides useful SSRF reduction but is disabled by default and does not constitute user authentication or tenant authorization.

The deployment templates are incomplete as standalone manifests: they contain substitution placeholders, the Service selector is `app: ${PROJECT_NAME}-service` while the StatefulSet labels are `app: ${PROJECT_NAME}-statefulset`, and the SSRF RBAC resources are not listed in the top-level kustomization. These should be resolved by the consuming deployment pipeline before relying on the manifests.
