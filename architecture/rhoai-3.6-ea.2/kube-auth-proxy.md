## Purpose

**Short**: kube-auth-proxy is a Go reverse proxy that authenticates requests with OpenShift OAuth or OIDC, then forwards authenticated requests to an upstream application.

**Detailed**: The proxy listens on a configurable HTTP and/or HTTPS address, manages OAuth/OIDC login and callback flows, validates sessions or bearer tokens, and injects authenticated user information into requests sent to configured upstreams. It is intended as a focused replacement for oauth-proxy sidecars in ODH/RHOAI deployments and also supports Kubernetes service-account token validation through the TokenReview API.

The repository supplies example Kubernetes Deployments, Services, a ServiceAccount, ConfigMaps, a Secret, and an OpenShift edge-terminated Route. The example proxy runs as a non-root user on port 4180 and fronts an `example-app` Service on port 8080. The examples are standalone manifests rather than a kustomize tree; platform operators or release packaging provide production composition and permissions.

## Architectural Analysis

kube-auth-proxy is a single Go executable with a layered HTTP pipeline: configuration is loaded from compatible legacy or alpha flags/configuration, provider-specific authentication establishes a session, middleware validates sessions or bearer tokens, and a reverse proxy forwards the request to the configured upstream. The implementation supports both external OIDC providers and OpenShift OAuth, with optional Kubernetes TokenReview validation for service-account callers. Session state can be held in encrypted cookies or an external Redis-compatible store.

The RHOAI-oriented build path is deliberately separated from the generic image path. `Dockerfile.konflux` builds with `CGO_ENABLED=1`, `GOEXPERIMENT=strictfipsruntime`, and `strictfipsruntime` tags, then copies the binary into a digest-pinned `ubi9/ubi-minimal-pqc` image. The application TLS layer defaults to TLS 1.2 through TLS 1.3, accepts configured cipher suites, and loads certificate/key material from configured secret sources. Production security therefore depends both on the FIPS build path and on deployment configuration: the example OpenShift Route terminates TLS at the edge, while the proxy's own HTTPS listener is optional.

The repository does not define CRDs, controllers, RBAC roles, NetworkPolicies, or kustomize overlays. The proxy's ServiceAccount and TokenReview permissions must consequently be supplied by the consuming deployment. The example ConfigMap allows all email domains (`*`) and forwards the access token and user headers; these are sample defaults that should be narrowed and reviewed for production use.
