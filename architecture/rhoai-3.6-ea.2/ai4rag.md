## Purpose

**Short**: ai4rag is a provider-agnostic engine that evaluates RAG template configurations and returns optimized RAG patterns.

**Detailed**: The package accepts documents, benchmark questions, a search-space definition, model implementations, and vector-store configuration. `AI4RAGExperiment` coordinates indexing, retrieval, generation, evaluation, and hyperparameter optimization, producing the best configuration and structured result artifacts.

The RAG pipeline is modular: document chunking, embeddings, vector storage, retrieval, and foundation-model generation are represented by replaceable interfaces. Built-in integrations use the OpenAI SDK for OpenAI-compatible model endpoints, direct clients for remote Milvus, embedded Milvus Lite, and PostgreSQL/pgvector, and boto3 for S3-compatible document discovery and download. The repository supplies reusable library code; orchestration in a separate pipeline-components repository consumes it.

## Architectural Analysis

ai4rag is an in-process Python library, not a server or operator. Its central design decision is dependency inversion around abstract foundation-model, embedding-model, vector-store, chunker, and RAG-template interfaces. This makes OpenShift AI MaaS one supported deployment target without coupling the package to Kubernetes APIs or a particular model provider.

An experiment first indexes documents, then evaluates candidate configurations through the RAG pipeline. The experiment engine caches evaluated configurations and can reuse vector-store collections when indexing parameters match. Model pre-selection can reduce large model combinations before the main optimizer runs; GAM and random optimizers are available. Query evaluation is parallelized and results can be streamed through event handlers.

The package supports three storage modes with deliberately different operational profiles: remote Milvus over an explicit HTTP(S) URI, local file-backed Milvus Lite for development and small workloads, and PostgreSQL with pgvector. The recent migration from ChromaDB to Milvus Lite makes local persistence explicit and avoids silently treating malformed remote configuration as a local database. Production deployment topology, replicas, network policy, and secret provisioning are outside this repository and must be supplied by the consuming pipeline or application.
