## Purpose

**Short**: Provides reusable Python components and complete Kubeflow Pipelines for data processing, AutoML, AutoRAG, evaluation, model deployment, and fine-tuning.

**Detailed**: The repository is a component and pipeline library rather than a long-running control-plane service. Components are compiled into Kubeflow Pipelines tasks and execute in task-specific runtime images. The library covers data ingestion and transformation, document parsing and retrieval-augmented generation, synthetic data generation, AutoML, model evaluation, model deployment, and fine-tuning workflows.

The repository also builds managed pipeline artifacts. The standard Dockerfile generates and initializes managed pipelines, while the Konflux AutoML and AutoRAG images package specialized component dependencies and offline Docling model artifacts. Runtime integrations include the Kubeflow Pipelines SDK, Kubernetes APIs and custom resources, S3-compatible storage, Hugging Face datasets, model registries, Milvus, and Ray/Kueue-based processing.

## Architectural Analysis

This component follows a compile-and-submit architecture: Python functions decorated with the KFP DSL define task interfaces, container images, package installation, artifact paths, and secret injection; the KFP compiler turns those definitions into pipeline specifications. Execution is distributed across task pods and, for document processing, a RayJob in a caller-supplied namespace. The repository itself does not expose an HTTP or gRPC server and has no CRDs, Services, Routes, or RBAC manifests.

The three Konflux images represent different dependency and supply-chain boundaries. AutoML and AutoRAG use the AIPCC CPU base image and install from Red Hat AI package indexes; AutoRAG additionally imports pinned Docling modelcars. The managed-pipelines image uses a pinned UBI Python base, explicitly enables the `DEFAULT:PQ` crypto policy, and installs a hashed requirements set. The general-purpose development Dockerfile uses a pinned UBI Python base and `uv sync` against the repository lock file.

The principal architectural risks are delegated authorization and data-plane configuration. Pipeline tasks receive credentials through Kubernetes Secrets and can operate on S3, PVC, Kubernetes, OCI, and model services. Namespace and service-account policy therefore remain outside this repository. In addition, AutoML has an SSL-error fallback that creates an S3 client with `verify=False`, which can permit an endpoint impersonation or man-in-the-middle condition after certificate failure.

## Multi-Tenancy

This repository is a library and does not define a tenant control plane. Tenancy is inherited from the KFP deployment, task namespace, service account, PVC, and backing data services. Several components accept a namespace explicitly, so callers can target a tenant namespace, but the repository does not enforce cross-tenant authorization itself.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | KFP-injected Secrets, service-account bearer token, external RBAC | Kubernetes/KFP | No Roles or bindings are shipped; over-privileged task accounts could cross namespaces |
| Data storage | Caller-selected PVC paths and S3 bucket/prefix | Kubernetes/storage service | Bucket and path isolation are not enforced by this library; shared credentials can widen access |
| Network traffic | No NetworkPolicy or AuthorizationPolicy in repository | Deployment platform | Default network posture is unknown |
| Compute & resources | KFP task resources, Ray worker counts, Kueue queue label, GPU selectors | KFP/Kubernetes/Kueue | `bypass_kueue` intentionally removes queue management for selected runs |
| Configuration & secrets | Namespace-local KFP Secret injection by named Secret | Kubernetes/KFP | Secret provisioning and rotation are external; some secrets are shared across multiple tasks |
| API scoping | Explicit namespace in RayJob/Kubernetes calls; external service APIs are endpoint/bucket configured | Application plus Kubernetes | No application-level tenant validation or cross-tenant filtering is implemented |
