## Purpose

**Short**: Builds and publishes Jupyter, Code Server, and execution-runtime workbench images for the ODH/RHOAI platform.

**Detailed**: The repository is a multi-image build system rather than a controller. It assembles Python 3.12 notebook and Code Server environments, with CPU, NVIDIA CUDA, and AMD ROCm variants, and publishes their references through ODH and RHOAI ImageStream manifests. The images are launched by the ODH Notebook Controller as user workbenches.

Jupyter images are layered from minimal through data-science and framework-specific variants such as PyTorch, TensorFlow, TrustyAI, and LLM Compressor. Separate runtime images provide Python environments for notebook or Elyra/Kale execution. Small Go utilities build `mongocli` and run check-payload-related image checks; they are build-time helpers, not platform control-plane services.

## Architectural Analysis

The repository separates reusable notebook layers from accelerator and framework overlays. This keeps CPU, CUDA, and ROCm variants structurally aligned while allowing the package lock and base image to select hardware-specific dependencies. The `runtime-*` images are intentionally separate from interactive Jupyter images, which supports execution workflows without requiring the full interactive stack.

Build reproducibility is a first-class design feature: image Dockerfiles copy lock files to invalidate stale layers, import RPM keys, install with no network index access, and consume Cachi2/Hermeto-prefetched RPMs, artifacts, and wheels. Most Konflux variants now use digest-pinned AIPCC images. The baseline CPU variants still use direct RHEL Python images, so their AIPCC migration status should remain visible to architecture consumers.

The analyzer found no controller, CRD, RBAC, ingress, or deterministic production API surface. The one HTTP endpoint/service observation points into CI cached-build test code and is explicitly treated as an unresolved candidate rather than a notebook server contract. Runtime network exposure, authentication, resource limits, and tenant isolation are therefore supplied by the consuming RHOAI/ODH deployment.
