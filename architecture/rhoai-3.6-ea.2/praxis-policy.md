## Purpose

**Short**: A pluggable Rust policy enforcement engine for evaluating authorization policies, resolving identities, delegating credentials, and applying request/response controls in a host gateway.

**Detailed**: praxis-policy is the public host facade for the Praxis Policy Enforcement Engine (PPE). It re-exports the policy runtime and can optionally compile built-in extensions for JWT identity, OAuth 2.0 token exchange, OIDC CIBA human approval, Cedar/CEL/OPA policy decisions, Valkey-backed sessions, audit logging, and PII scanning.

The workspace is designed to be embedded by a gateway or other host rather than deployed as an independent Kubernetes workload. The host supplies request metadata, registers plugins and policy configuration, and normally injects the host's HTTP transport. The engine evaluates APL policy through hook-specific plugin invokers, supports fail-closed policy and capability checks, and can project trusted assertion headers to an upstream service.

## Architectural Analysis

The workspace separates policy language, execution, host integration, and optional capabilities into independently publishable Rust crates. `praxis-policy-core` owns the `PolicyEngine`, hook execution, configuration loading, route selection, capability gating, and host service traits; APL core/runtime/CMF crates translate policy documents and host extension data into executable hook invocations. Cedar, CEL, and embedded OPA/Rego are alternative PDP implementations, while `ppe-pdp-diff` provides differential agreement tests across them.

Network access is deliberately a host concern. The optional `http-hyper` feature supplies a default `hyper`/`rustls` transport, but the documented deployment path injects a host transport so the embedding process retains one connection pool, trust store, and egress policy. The shared private-address table is intended to prevent SSRF destinations, but enforcement depends on the transport checking the address at connection time. This makes host wiring and deployment-level egress policy material security dependencies.

The engine has no Kubernetes deployment topology in this checkout. Tenant identity can be represented in JWT claims and policy attributes, and the Valkey session plugin can use a shared external store, but namespace/RBAC/network isolation is outside this repository. Consumers must provide those boundaries and ensure policy configuration and tenant-derived attributes cannot be altered by less-trusted callers.
