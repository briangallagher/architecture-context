## Purpose

**Short**: Provides the upstream Kubeflow Notebook controller and the RHOAI/ODH extension that provisions notebook workloads, Gateway API routes, authorization proxies, and notebook-scoped policies.

**Detailed**: The upstream controller watches namespaced `kubeflow.org` Notebook resources and reconciles StatefulSets, Services, Pods, Events, and optional idle-notebook culling. It is the workload reconciler for the notebook runtime and preserves Notebook ownership links so Kubernetes garbage collection removes derived resources.

The ODH controller extends that lifecycle with OpenShift/RHOAI integration. It creates a central-namespace Gateway API HTTPRoute to a notebook service, optionally injects a kube-rbac-proxy sidecar and its supporting ServiceAccount, Service, ConfigMap, RBAC bindings, certificates, and network policies, and integrates with data science pipelines, MLflow, Feast, ImageStreams, and trusted CA bundles. It also exposes fail-closed mutating and validating admission webhooks.

## Architectural Analysis

This checkout is an integration repository containing two separately built controller images. The upstream controller owns the notebook StatefulSet and service lifecycle; the ODH controller observes the same Notebook API and adds platform-facing resources. The ODH route is deliberately created in the controller's protected central namespace while its backend Service remains in the user's namespace. A ReferenceGrant and explicit finalizer-based cleanup bridge that cross-namespace relationship, avoiding unsupported cross-namespace owner references.

The primary RHOAI access path is Gateway API: `/notebook/{namespace}/{name}` is routed either directly to port 8888 or through a per-notebook kube-rbac-proxy Service on port 8443. Authorization is delegated to Kubernetes SubjectAccessReview for `get` on the named Notebook. Notebook-scoped NetworkPolicies restrict ingress to the notebook and proxy ports. The main architectural risk is the intentionally broad cluster-level controller authority required to watch and create resources across user namespaces, combined with shared central HTTPRoute management; labels, namespace-qualified paths, RBAC, and finalizers are important correctness and isolation controls.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-notebook kube-rbac-proxy and named Notebook SubjectAccessReview | Kubernetes RBAC / proxy | Controller has broad cross-namespace authority; proxy injection is annotation-controlled. |
| Data storage | Notebook-owned namespaced workloads and Services | Kubernetes namespace/owner references | No external multi-tenant database isolation is implemented here. |
| Network traffic | Notebook and proxy NetworkPolicies | Kubernetes NetworkPolicy | Policy coverage depends on cluster NetworkPolicy enforcement. |
| Compute & resources | Per-notebook StatefulSet; proxy resource defaults configurable by annotations | Kubernetes scheduler/controller | No ResourceQuota or node isolation is created by these controllers. |
| Configuration & secrets | Namespaced ConfigMaps/Secrets; informer cache strips payloads and direct-reads sensitive data | Kubernetes plus controller cache transform | Shared trusted CA ConfigMaps are watched cluster-wide by design. |
| API scoping | Notebook namespace/name labels and namespace-scoped backend Service; central route list filtered by both labels | Controller code / Kubernetes API | Central namespace route management relies on label correctness because cross-namespace owner references are unavailable. |

### Shared Services

| RHOAI Gateway | Path embeds tenant namespace and Notebook name | HTTPRoute labels, namespace-qualified backend, ReferenceGrant, and Gateway policy |
