## Purpose

**Short**: Deploys and reconciles namespace-scoped Kubeflow Data Science Pipelines application stacks on OpenShift.

**Detailed**: DSPO watches `DataSciencePipelinesApplication` (DSPA) resources and renders the configured pipeline stack into the DSPA namespace. The stack can include the KFP API server, Argo workflow components, persistence and scheduled-workflow agents, ML Metadata services, database/object storage, network policies, RBAC, Routes, and monitoring resources.

The controller uses controller-runtime and Manifestival templates. Configuration and image references are projected from ConfigMaps and environment variables; database and object-storage connectivity is checked before dependent workloads are reconciled. RHOAI deploys the operator in `redhat-ods-applications`, while DSPA instances provide the namespace boundary for tenant workloads.

## Architectural Analysis

DSPO is a cluster-level control-plane component with a per-namespace data-plane pattern: one DSPA describes one pipeline installation, and the reconciler creates the associated services, service accounts, secrets, workloads, routes, and NetworkPolicies in that namespace. This keeps pipeline execution and credentials close to the namespace tenant while allowing the operator to observe and manage the required cluster APIs.

The pipeline store has two modes. Database-backed storage uses MariaDB or an external MySQL-compatible endpoint; Kubernetes-backed storage uses Pipeline and PipelineVersion CRDs and conditionally creates a shared `ds-pipelines-webhook`. The webhook is removed only when no remaining DSPA uses Kubernetes storage, so its lifecycle is intentionally coordinated across namespaces.

TLS is profile-driven for the controller and service-CA-backed for generated internal services. The Konflux build uses a UBI minimal PQC runtime and explicitly builds with `CGO_ENABLED=0`, `GOFIPS140`, and `no_openssl`; this is a material distinction from a dynamically linked check-payload FIPS build and should be treated as a build-compliance risk until downstream validation establishes otherwise.

## Data Flows

1. A user or dashboard submits a DSPA or pipeline request through Kubernetes or a generated OpenShift Route.
2. DSPO reads the DSPA, configuration, credentials, and dependent platform resources, then renders resources into the DSPA namespace.
3. The API server stores metadata in MariaDB and artifacts in S3-compatible storage, while Kubernetes-backed mode stores Pipeline/PipelineVersion objects and uses admission webhooks.
4. Argo executes workflow resources and creates pipeline pods; persistence and scheduled-workflow components synchronize or trigger runs.
5. MLMD records artifact and execution lineage; internal traffic is protected by service-CA TLS and NetworkPolicies when enabled.
