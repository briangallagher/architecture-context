## Purpose

**Short**: Provides the model-registry REST API and supporting catalog, UI, storage-initialization, upload, and KServe integration components for registering and serving model metadata.

**Detailed**: The primary Go binary exposes the Model Registry API, persists model, version, artifact, experiment, metric, serving-environment, and inference-service metadata through the embedded OpenAPI/data-store implementation, and provides readiness endpoints. Kubernetes manifests deploy it as a single-replica namespaced service backed by a ClusterIP on port 8080; database-backed overlays supply MySQL/PostgreSQL connection settings and credentials.

The repository also packages a Go UI BFF and static frontend, a model catalog plugin server, a Python async-upload worker, and a CSI storage initializer. A separate Go controller watches namespaced KServe `InferenceService` objects and synchronizes their model-serving state into the Model Registry through its REST API. The controller and BFF use Kubernetes API credentials and RBAC, while external UI/API traffic is routed through Istio and authenticated by gateway or bearer-token policy.

## Architectural Analysis

This is a hub-style multi-component repository rather than a single deployable workload. The model-registry API is the shared state authority; the UI BFF and KServe controller are clients of that API, while the catalog and async-upload components add discovery and artifact-ingestion capabilities. The controller’s namespace label and service lookup allow an `InferenceService` to select a registry in its namespace, with a configured default namespace as fallback.

The deployment surface has upstream/default kustomize material plus ODH, PostgreSQL, MySQL, catalog, UI, controller, CSI, and Istio options. The main service runs non-root with dropped capabilities and an Istio sidecar, but its base service is HTTP and the database credentials are supplied through Kubernetes Secret references. The Istio authorization policy constrains internal JWT-bearing calls to the `kubeflow` namespace and permits gateway-originated user traffic; this is an important control against cross-tenant in-mesh access.

Build reproducibility is mixed: Go modules have `go.sum`, the async-upload Python path has `poetry.lock` and a pinned requirements file, and the Konflux async-upload image is digest-pinned and based on AIPCC CPU. Other images use mutable `latest` or build-argument-selected bases, and no RPM or Hermeto lock files were found in the checkout. Several Go images use `CGO_ENABLED=0`, while the ODH image uses `CGO_ENABLED=1`; release-level FIPS status therefore depends on which image is built and the downstream image gate.
