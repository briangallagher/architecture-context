## Purpose

**Short**: Watches RHOAI `AITenant` resources and installs a tenant-specific Praxis external-processing dataplane for tenants that opt into the Praxis backend.

**Detailed**: `ai-gateway-controller` is a controller-runtime manager deployed in the `opendatahub` namespace. Its active reconciler watches the MaaS `maas.opendatahub.io/v1alpha1` `AITenant` resource. An annotation selecting `praxis`, together with `status.phase=Active` and a resolved `status.gatewayRef`, authorizes installation into the tenant's gateway namespace.

For an opted-in tenant, the controller builds the vendored `praxis-extproc` Kustomize overlay, substitutes the tenant gateway, image, and MaaS route values, renames resources with a tenant suffix, and server-side-applies them. The resulting pre-processing and post-processing gRPC services are connected to the MaaS Gateway through an Istio `EnvoyFilter`. The controller also owns cleanup through a finalizer when a tenant changes backend or is deleted. `ExternalModel` and `ExternalProvider` APIs are defined in this checkout, but the branch's implemented controller registration is the `AITenant` reconciler; model/provider reconciliation is documented as future work in `DESIGN.md`.

## Architectural Analysis

The component is a control-plane fan-out controller rather than a request-serving API. It bridges the platform tenant lifecycle owned by `maas-controller` to a shared, vendored Praxis deployment model. Tenant readiness is deliberately gated on both the active phase and the gateway reference, while steady-state drift is corrected by a five-minute requeue. Resource names, labels, Service selectors, ServiceAccount references, ConfigMap mounts, Envoy upstream addresses, and SNI values are rewritten together so multiple tenant instances can coexist in a gateway namespace.

The dataplane has two ext-proc stages. Pre-processing extracts the model name before authentication and fails open; post-processing performs the full request/response processing after authentication and fails closed. The EnvoyFilter contains compatibility anchors for multiple Istio/Kuadrant/RHCL versions and disables both filters on MaaS API management routes. This is operationally powerful but couples the component to gateway filter names, route naming, and self-signed certificate behavior. The current design also shares a ClusterRole across tenant bindings and permits the DestinationRule/Envoy upstream validation bypass required by the non-mesh Praxis service, which should remain an explicit security review item.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-tenant ServiceAccount and binding; shared reader ClusterRole | Kubernetes RBAC | ClusterRole grants cluster-wide reads to each bound dataplane; least-privilege is limited by the shared design. |
| Data storage | No persistent data store; ConfigMap and Secret references are namespaced where provider APIs require it | Kubernetes | Shared cluster-wide RBAC for ext-proc readers can expose resources beyond a tenant namespace. |
| Network traffic | Tenant-specific NetworkPolicy selects suffixed dataplane pods; ingress restricted to gateway pods and monitoring namespaces | Kubernetes NetworkPolicy | Policy allows Kubernetes API ports and relies on platform namespace labels. |
| Compute & resources | Per-tenant Deployments, fixed requests/limits, one replica | Kubernetes scheduler | No ResourceQuota/LimitRange or node isolation is created by this component. |
| Configuration & secrets | Per-tenant ConfigMap, ServiceAccount, and Secret reads | Kubernetes namespace/RBAC | Provider Secret rotation is external and not managed here. |
| API scoping | `AITenant` watch is cluster-wide; rendered resources target `status.gatewayRef.namespace`; ExternalModel/Provider refs must be same namespace | controller code and Kubernetes API | Controller can read and create cluster-scoped RBAC objects; correctness depends on validated gateway references from `maas-controller`. |
