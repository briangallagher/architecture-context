## Purpose

**Short**: Provides Kubeflow Workspaces by reconciling Workspace and WorkspaceKind resources into per-workspace runtime resources and access paths.

**Detailed**: The component is the Kubeflow Notebooks v2 workspaces subsystem. Its controller watches namespaced `Workspace` objects and cluster-scoped `WorkspaceKind` definitions, then creates and maintains the StatefulSet, Service, ServiceAccount, RoleBinding, and optional Istio VirtualService resources required for an interactive workspace. Workspace cleanup also removes cross-namespace HTTPRoutes and cluster-scoped authorization bindings through a finalizer.

The repository also contains a Go backend that serves the workspace API, OpenAPI/Swagger assets, static frontend assets, logs, metrics, PVCs, and namespace-scoped secrets. A React/TypeScript frontend consumes that API. Gateway API support can expose workspaces through HTTPRoutes in a configured Gateway namespace; an alternate Istio VirtualService path is supported. The controller and webhook are deployed from kustomize bases and optional cert-manager, Gateway API, Istio, OpenShift-webhook, and Prometheus components.

## Architectural Analysis

The design separates declarative workspace intent (`Workspace` and `WorkspaceKind`) from runtime realization. `WorkspaceKind` is cluster-scoped so administrators can publish reusable workspace definitions, while each `Workspace` is namespaced and owns the user-facing runtime resources. The controller uses owner references for same-namespace resources and a finalizer for cross-namespace or cluster-scoped resources that cannot use owner references.

The controller has broad Kubernetes privileges because it creates workspace workloads, service accounts, bindings, services, and networking resources. In particular, the explicit `clusterroles: bind` permission is intentional: administrator-selected ClusterRoles from a WorkspaceKind can be bound to a workspace ServiceAccount. This is a significant trust boundary and should remain limited to trusted WorkspaceKind authors.

Analyzer coverage did not establish workloads, Services, RBAC rows, or complete deployment topology even though the repository contains corresponding manifests. Those facts below are therefore sourced directly from manifests and code where available; analyzer-confirmed inventories remain distinguished from source-derived enrichment.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-workspace ServiceAccount and namespaced RoleBindings; controller has cluster-wide management RBAC | Kubernetes RBAC | `clusterroles: bind` allows administrator-selected ClusterRole grants |
| Data storage | Workspace PVCs and Secrets are namespace-scoped | Kubernetes and controller | Shared backend behavior is not independently tenant-authenticated by analyzer |
| Network traffic | Default-deny ingress policy in `kubeflow-workspaces`; optional Istio/Gateway policies | Kubernetes/Istio | Full per-tenant network policy set is configuration-dependent |
| Compute & resources | Separate StatefulSet per Workspace; WorkspaceKind specifies runtime resources | Kubernetes/controller | Quota/LimitRange enforcement is delegated to the cluster |
| Configuration & secrets | Namespace-scoped Workspace resources and referenced Secrets/ConfigMaps | Kubernetes/controller | Controller can read cluster-wide ConfigMaps and Secrets are deliberately uncached; exact filtering is implementation-specific |
| API scoping | Backend handlers use namespace path parameters; controller reconciles `req.NamespacedName` | Application/Kubernetes | Analyzer did not fully verify every API handler authorization path |
