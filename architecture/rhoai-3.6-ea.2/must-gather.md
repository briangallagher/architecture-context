## Purpose

**Short**: Collects Red Hat OpenShift AI and LLM-D cluster state, custom resources, manifests, pod specifications, and logs for support and diagnostics.

**Detailed**: The image is launched by `oc adm must-gather` or as a Kubernetes Job. Its entrypoint detects the Kubernetes distribution, selects `oc` for OpenShift or `kubectl` for xKS environments, establishes configurable namespace defaults, and gathers cluster and component data into the must-gather destination directory. It is an observability and evidence-collection tool rather than a continuously running platform service.

On OpenShift, the collector inspects the operator, application, notebook, monitoring, model registry, ingress, Kuadrant, and Helm namespaces, records the RHOAI version, and collects platform component configuration resources. The default `all` mode starts the component collectors concurrently; `COMPONENT` selects one collector. On non-OpenShift Kubernetes, collection is focused on LLM-D and its dependencies, with optional workload-variant autoscaler and batch-gateway collection.

## Architectural Analysis

The architecture is a shell orchestration layer over native Kubernetes inspection commands. `common.sh` supplies shared namespace discovery, resource collection, Helm release capture, and log-window handling. Each component script declares the resource kinds relevant to its domain, discovers namespaces containing those resources, and runs collection concurrently. The xKS utility adds auto-discovery of all namespaced or cluster-scoped resource kinds and a `kubectl_inspect` implementation that captures YAML and current/previous container logs.

The collector is deliberately broad: it records both platform control-plane objects and workload namespaces, including Gateway API, Istio, monitoring, serving, training, workflow, model, tenancy, and operator resources. This makes the output useful for cross-component diagnosis, but the cluster-wide read scope and collection of pod logs mean the resulting artifact can contain sensitive configuration or operational data. The image has no persistent data store or application API of its own; its dependencies and security posture are inherited from the Kubernetes credentials, base must-gather image, and command-line clients available at runtime.
