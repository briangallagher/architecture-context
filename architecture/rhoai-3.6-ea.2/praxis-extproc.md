## Purpose

**Short**: Runs configurable Praxis filter pipelines as an Envoy External Processing gRPC service.

**Detailed**: `praxis-extproc` translates Envoy HTTP external-processing messages into Praxis requests and responses. It receives request/response headers and buffered bodies, executes a shared filter pipeline, and returns header mutations, body replacements, or immediate responses to Envoy.

Envoy remains responsible for the HTTP data plane, routing, upstream connections, and gateway integration. The service runs a main ExtProc gRPC listener plus separate gRPC health and Prometheus metrics listeners. The RHOAI deployment uses two EnvoyFilter instances conceptually: a failure-tolerant pre-processing pipeline and a fail-closed main processing pipeline.

## Architectural Analysis

This is a stateless, single-container Rust adapter between the RHOAI/MaaS gateway Envoy data plane and Praxis filter implementations. Configuration is loaded from a mounted YAML ConfigMap at startup; named filter chains are flattened into one immutable, shared `FilterPipeline`, while each ExtProc stream gets its own filter context. This keeps filter definitions centralized and permits concurrent request streams without per-request deployment state.

The deployment intentionally separates the application protocol from operational endpoints. The Kubernetes Service exposes only the ExtProc port, while health and metrics are container listeners used by probes and monitoring. The ODH overlay renames the rendered service for pre-processing, injects the workload into the gateway through Istio EnvoyFilter patches, and adds a DestinationRule because the gateway-to-service connection uses TLS to a non-mesh service.
