## Purpose

**Short**: A configurable vLLM-compatible inference simulator for testing OpenAI-style HTTP APIs, gRPC inference, latency behavior, and KV-cache integrations.

**Detailed**: The simulator provides deterministic or randomized model responses without running a full model-serving engine. It exposes OpenAI-compatible completion, chat, responses, messages, embeddings, rendering, tokenization, model, health, metrics, administrative, sleep/wake, and LoRA-management endpoints. Runtime behavior is configured with command-line flags or YAML/JSON configuration, including model identity, latency profiles, failure simulation, and optional KV-cache event handling.

The main Go process listens on one TCP port and uses cmux to multiplex HTTP/1.1 and HTTP/2 gRPC traffic. In the Kubernetes deployment it runs beside a native vLLM render sidecar on localhost:8082 for tokenization/rendering, while a NodePort exposes the simulator on port 8000. A separate Dockerfile.zmq image packages a Python ZeroMQ listener for KV-cache test scenarios; it is an auxiliary test/development artifact rather than part of the primary Deployment.

## Architectural Analysis

The component is a test double for vLLM’s serving surface. The communication layer owns common HTTP APIs and delegates engine-specific routes to the vLLM engine implementation. A simulator processor generates responses from echo/random/custom-dataset modes and records Prometheus metrics; the dataset tool can build tokenized response datasets through the render service. KV-cache support uses llm-d-router types and optional ZeroMQ event/replay paths.

The deployment is intentionally small and single-replica, with no readiness or liveness probe on the simulator container itself. The render sidecar has startup, liveness, and readiness probes, and the simulator waits for its startup through native-sidecar ordering. Configuration and image values are substituted by the deployment environment rather than embedded in a platform operator API.
