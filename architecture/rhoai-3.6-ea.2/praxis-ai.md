## Purpose

**Short**: Praxis AI is a configurable, high-performance AI gateway that classifies, transforms, filters, and routes provider-native HTTP traffic.

**Detailed**: The workspace extends the Praxis proxy with AI-specific API types, provider protocol translation, routing, credential injection, prompt and payload processing, agentic MCP/A2A handling, guardrails, token accounting, and OpenAI Responses/Conversations persistence. The `praxis-ai` binary assembles core Praxis filters with AI filters and optional llm-d `ext_proc` support into listener-specific pipelines.

The service is intentionally policy-driven: runtime YAML selects listeners, filter chains, clusters, TLS, and optional stores. A shared sub-request client provides pooled outbound calls and optional circuit breakers. Configuration can be loaded from a file, validated or dumped through the CLI, and hot-reloaded by a file watcher. The repository also contains reusable `apis`, `filters`, and llm-d compatibility crates alongside the server and test/tooling crates.

## Architectural Analysis

Praxis AI is an in-process filter pipeline around the Praxis/Pingora runtime. The server resolves named filter chains for HTTP and TCP listeners, registers core and AI filters, and passes traffic through provider-aware transformations before forwarding it to configured upstream clusters. This keeps most AI behavior inside one process and avoids a network hop between filters; the optional llm-d compatibility filter deliberately introduces a streaming gRPC hop only where the EPP protocol requires it.

The repository separates protocol/domain concerns into libraries: `apis` owns wire formats, validation, translation, and response storage; `filters` owns composable request/response behavior; `integrations/llmd/ext-proc` owns Envoy external-processing compatibility; and `server` owns startup, registration, health checks, reload, and runtime limits. The image builds only the server binary, while the complete workspace remains available for tests and development.

Operationally, the image exposes a configurable proxy listener and a separate admin/health listener. The built-in configuration binds them to loopback, while production topology, TLS, authentication, and upstream destinations are supplied by Praxis configuration. The analyzer found no Kubernetes deployment manifests, CRDs, RBAC, or ingress objects in this repository, so those concerns are external to this checkout.
