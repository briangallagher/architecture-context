## Purpose

**Short**: A Python framework and containerized batch runtime for evaluating language models across standardized benchmarks and custom tasks.

**Detailed**: lm-evaluation-harness provides the `lm_eval` Python package and `lm-eval`/`lm_eval` console commands. It normalizes evaluation across local Hugging Face, vLLM, SGLang, API-hosted, and other model backends, then executes benchmark tasks, metrics, generation, and result logging.

The RHOAI image is a one-shot execution environment rather than a continuously running service. The Konflux image installs the harness with API, ifeval, math, and IBM watsonx extras, prepares writable locations for Hugging Face data, outputs, custom tasks, and Unitxt catalogs, and runs as UID 65532. It supports CPU and NVIDIA CUDA base-image variants across x86_64, aarch64, ppc64le, and s390x build targets.

## Architectural Analysis

The component is a library-plus-job image. Its primary runtime boundary is the CLI, while model adapters and task definitions are plug-in-like Python modules loaded by the evaluation driver. The image does not define Kubernetes controllers, CRDs, Services, ingress, or an application listener; orchestration is supplied by the surrounding RHOAI evaluation workflow and Tekton build configuration.

The architecture deliberately keeps model execution flexible: local models can use CPU/GPU libraries such as PyTorch, Transformers, PEFT, vLLM-related integrations, or multimodal adapters, while remote providers can be reached through HTTP clients and provider SDKs. This makes the harness broadly reusable but means outbound endpoints, credentials, downloaded model/task content, and runtime resource limits are deployment concerns rather than centrally enforced by this repository.

The Konflux Dockerfile consumes AIPCC CPU and CUDA base images and installs the application on top. The release pipeline requests hermetic prefetch for pip and RPM inputs and builds a multi-architecture image index. The separate legacy Dockerfile builds native Arrow, PyTorch, and OpenBLAS artifacts from a UBI Python image, so the two image paths have materially different supply-chain and accelerator behavior.
