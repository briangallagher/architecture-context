## Purpose

**Short**: llm-d Planner turns LLM workload requirements into GPU capacity estimates, ranked deployment recommendations, and Kubernetes deployment bundles.

**Detailed**: The component provides a Python library, REST API, and Streamlit user interface for translating business requirements into SLOs, selecting model/GPU configurations, estimating capacity and performance, and generating or deploying Kubernetes manifests for LLM serving workloads. It combines bundled benchmark data with Hugging Face model metadata, optional RHOAI Model Catalog data, and LLM providers such as Ollama, OpenAI-compatible APIs, or Vertex AI.

The deployed application is split into a FastAPI backend on port 8000 and a Streamlit UI on port 8501. A separate Ollama deployment supplies the default local LLM provider. An optional vLLM-compatible simulator exposes completion and metrics endpoints for GPU-free development and end-to-end tests. The backend also reads cluster node data through a narrowly scoped ClusterRole and can call the RHOAI Model Catalog over service TLS.

## Architectural Analysis

llm-d Planner is an application-level orchestration and planning service rather than a Kubernetes operator: it has no CRDs, watches, reconciliation loop, or admission webhooks. Its Kubernetes integration is imperative and user-facing. The backend can inspect nodes, generate KServe/vLLM-oriented YAML, query deployment status, and submit deployment actions, while the manifests in this repository provide the planner's own runtime and supporting services.

The runtime topology is intentionally simple but has several environment assumptions. The backend uses a single replica and a ReadWriteOnce SQLite PVC; Ollama also uses a single replica with a Recreate strategy and a 20 GiB model PVC. The UI reaches the backend through an in-cluster HTTP Service, while both UI and backend have edge-terminated OpenShift Routes. External model and LLM providers are selected through ConfigMap values and credentials in a shared namespace Secret.

The repository is not yet aligned with the RHOAI secure-build conventions described by the AIPCC reference: its Dockerfiles use upstream `python:3.14-slim` images, install packages with pip/uv, and do not use Konflux-suffixed files, AIPCC base images, or RPM/artifact lock files. The branch does contain a Python lockfile reference in the backend Dockerfile (`uv sync --frozen`), but no `uv.lock` was present in the checkout, so the documented container build is not reproducible from the checked-out source alone.
