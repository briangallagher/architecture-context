## Purpose

**Short**: Reconciles namespaced `LLMBatchGateway` resources into a complete batch-gateway deployment, including API server, processor, garbage collector, optional async processor, routing, TLS, credentials, and monitoring resources.

**Detailed**: The operator watches `LLMBatchGateway` custom resources and translates each specification into Helm values. It renders the prefetched batch-gateway and async-processor charts in-process, assigns ownership to the custom resource, and applies the resulting Kubernetes objects with server-side apply. It also removes owned resources that are no longer desired and publishes component readiness in the CR status.

The operator receives four platform-selected component image references through environment variables rather than from the user CR. It supports synchronous and asynchronous dispatch, S3 or PVC-backed file storage, Redis/Valkey or PostgreSQL state storage, API-server HTTPRoute exposure, cert-manager certificates, OpenTelemetry, and Prometheus monitoring. Cross-namespace credential references are allowed only through Gateway API `ReferenceGrant` and are copied into the workload namespace.

## Architectural Analysis

This is a single-manager, controller-runtime operator whose principal boundary is the namespaced `LLMBatchGateway` CR. The reconciliation pipeline is deliberately declarative: CR fields become Helm values, rendered chart objects become unstructured Kubernetes resources, and owner references plus periodic resynchronization provide drift correction. The operator therefore centralizes lifecycle management while leaving the data plane in the chart-managed workloads.

The deployment is modular at runtime. A CR normally produces API-server, processor, and GC workloads; async mode additionally produces the async processor. Optional CRDs are detected through the REST mapper before watches or ownership handling are installed, allowing the manager to start on clusters without cert-manager, Gateway API, or Prometheus Operator. API traffic is exposed through a chart-generated Gateway API HTTPRoute when enabled, while the operator's own metrics use a service-ca-issued HTTPS service and bearer-token authorization.

The strongest security controls are Kubernetes RBAC, namespace scoping, ReferenceGrant-gated secret copying, TLS profile propagation, non-root/read-only operator execution, and immutable image inputs. Important residual risks are that S3 tenant separation relies on key prefixes in a shared bucket, network policies and quotas are not created here, and the API/metrics authentication behavior of chart-generated resources is configuration-dependent.
