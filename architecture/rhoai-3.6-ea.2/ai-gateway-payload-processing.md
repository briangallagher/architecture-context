## Purpose

**Short**: Provides pluggable request and response processing for an AI Gateway and reconciles model/provider configuration into Kubernetes and Istio routing resources.

**Detailed**: The component runs the llm-d Inference Payload Processor framework as an Envoy External Processing gRPC service. Its configured plugin chain can mutate request and response headers/bodies, select providers, translate provider protocols, enforce stream usage, and inject provider credentials. The controller-runtime manager also reconciles `ExternalModel` and `ExternalProvider` resources.

`ExternalProvider` reconciliation validates a namespace-local credential Secret and creates an `ExternalName` Service, Istio `ServiceEntry`, and TLS-origination `DestinationRule` for the provider endpoint. `ExternalModel` reconciliation resolves namespace-local provider references and creates an `HTTPRoute` under the configured Gateway, with a default 300-second route timeout. A conditional legacy migration controller converts legacy `maas.opendatahub.io` model resources when that CRD is installed.

## Architectural Analysis

This is a controller-plus-data-plane component packaged as one Go binary. The controller-runtime manager watches configuration CRs and generated networking resources while the same process serves the Envoy ExtProc and health gRPC endpoints. The request path is therefore: Gateway/Envoy ExtProc callout → configured llm-d plugin pipeline → provider selection, translation, and credential injection → routed external provider.

The provider abstraction keeps external endpoints behind namespace-local Kubernetes Services and Istio resources. Model routes use a namespace/model path and provider header matches to select backends. Hub-mode Helm examples support separate pre- and post-processing deployments for cross-cluster routing. The principal operational risks are configuration-dependent ExtProc TLS, unauthenticated health and gRPC application surfaces, and the broad permissions required by multi-namespace mode.
