## Purpose

**Short**: A cluster-scoped operator that provisions and maintains the RHOAI observability stack for metrics, traces, usage logs, dashboards, and alerting.

**Detailed**: The operator reconciles a singleton `services.platform.opendatahub.io/v1alpha1` `Monitoring` resource. It discovers prerequisite APIs at runtime and renders only the enabled observability subsystems, including Cluster Observability Operator Prometheus/Thanos resources, Tempo, OpenTelemetry Collector, Perses dashboards, alerting rules, and supporting RBAC, services, routes, TLS, and network policies.

Resources are rendered from embedded Go templates and applied with server-side apply through `odh-platform-utilities`, with label-based ownership and garbage collection because a cluster-scoped CR cannot own namespace-scoped operands through OwnerReferences. A mutating admission webhook injects the monitoring scrape label into PodMonitor and ServiceMonitor objects in opted-in namespaces.

## Architectural Analysis

This is a control-plane component with a deliberately adaptive deployment model: prerequisite CRD discovery gates each subsystem, while the singleton cluster-scoped `Monitoring` object provides the desired state and a namespace field selects the operand namespace. The reconciler watches the managed CR and generated Kubernetes resources, cluster TLS configuration, and prerequisite APIs, then converges the generated resource set and status conditions.

The data plane is composed of shared monitoring and tracing systems plus two Prometheus access paths. The cluster proxy fronts cluster metrics with `kube-rbac-proxy`; the namespace proxy combines `prom-label-proxy` with a TLS-authenticated proxy to constrain namespace-oriented access. OpenShift Routes expose the proxy and Thanos query surfaces, while NetworkPolicies gate collector and Prometheus ingress. The main architectural risk is the breadth of cluster RBAC and shared observability services: tenant isolation depends on Kubernetes authorization, namespace labels, proxy configuration, and generated policy remaining consistent.

## Data Flows

### Flow 1: Monitoring reconciliation

`Monitoring` CR → controller-runtime watch → prerequisite CRD/operator discovery → embedded template selection and rendering → server-side apply to monitoring namespace → status/condition aggregation and stale labeled-resource garbage collection.

### Flow 2: Metrics access

Prometheus/Thanos → TLS service/proxy → `kube-rbac-proxy` authorization → cluster or namespace query path → authorized client. Collector telemetry is exposed through TLS-enabled `:8890` and Prometheus scrape service `:8889`, gated by generated NetworkPolicies.

### Flow 3: Monitor admission

API server → TLS webhook service `:9443` → PodMonitor/ServiceMonitor decoder → namespace label and singleton Monitoring lookup → JSON patch adding `monitoring.opendatahub.io/scrape=true`, or allow without mutation.
