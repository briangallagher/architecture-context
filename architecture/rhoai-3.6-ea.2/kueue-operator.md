## Purpose

**Short**: Deploys and configures Kueue on OpenShift, including its controller manager, admission webhooks, certificates, RBAC, network policies, and monitoring resources.

**Detailed**: The operator watches the cluster-scoped `kueue.openshift.io/v1 Kueue` configuration resource and reconciles the upstream Kueue control plane into `openshift-kueue-operator`. It supplies the operand image through `RELATED_IMAGE_OPERAND_IMAGE`, creates the Kueue deployment and services, and manages the Kueue CRDs and admission configurations.

The operand provides workload admission, mutation, validation, queueing, visibility, and metrics for Kubernetes workloads and supported ML workload APIs. The operator uses Kubernetes typed, dynamic, discovery, OpenShift Route, and CRD clients and starts namespace-aware informers for the operator namespace and cluster-wide resources.

## Architectural Analysis

This is a two-tier control plane: the OpenShift-specific operator watches the cluster-scoped `Kueue` configuration and reconciles an embedded/generated Kueue operand, while the operand performs workload queueing, admission mutation/validation, visibility, and metrics. This separation lets the distribution-specific operator own OpenShift lifecycle, certificates, RBAC, and platform integration while reusing upstream Kueue behavior.

The primary tenancy boundary is Kubernetes-native. Workloads and LocalQueues are namespaced, while ClusterQueues and operator configuration are cluster-scoped; admission is opt-in through the `kueue.openshift.io/managed=true` namespace label. The control plane is shared across opted-in namespaces and relies on RBAC, admission namespace selectors, Kueue queue configuration, and default-deny NetworkPolicies rather than an application database or per-tenant service deployment.

The analyzer establishes the manifest-level APIs, services, RBAC, webhooks, certificates, and network policies. It does not establish exact runtime handler behavior, controller-watch coverage, TLS protocol/cipher settings, or binary linking. The presence of an OpenShift Route client is therefore recorded as a possible integration surface, while no generated ingress route is claimed. The operator’s broad cluster permissions, including RBAC bind/escalate capabilities, and fail-closed admission webhooks are important deployment security and availability boundaries.

## Synthesis Notes

This is a two-layer control plane: a small OpenShift-specific operator manages an embedded/generated Kueue operand, while the operand supplies the actual queueing and admission behavior. The operator's use of typed, dynamic, discovery, CRD, and OpenShift Route clients reflects reconciliation across both Kubernetes and OpenShift API surfaces.

The primary isolation model is Kubernetes-native: one cluster-wide control plane, namespace-scoped workloads and LocalQueues, cluster-scoped scheduling policy, opt-in webhook selection, RBAC, and NetworkPolicies. The default-deny policy is a strong network baseline, but the operator and operand share an operator namespace and the operator has broad cluster permissions including RBAC `bind` and `escalate`; deployment ownership and role review are therefore important security boundaries.

The analyzer confirms manifest-level services, CRDs, RBAC, and webhooks but does not prove all runtime HTTP handlers or controller watches. In particular, the OpenShift Route client indicates a possible dynamic integration while no route was confirmed in the bounded inventory. Exact webhook mutation/validation semantics, TLS versions/cipher suites, and binary linking/FIPS behavior remain unknown unless established by runtime or build inspection outside this artifact's evidence boundary.
