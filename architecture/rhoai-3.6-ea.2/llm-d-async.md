## Purpose

**Short**: Consumes asynchronous inference requests from Redis/Valkey or Google Cloud Pub/Sub, applies dispatch and concurrency policies, sends requests to an inference gateway, and publishes results.

**Detailed**: llm-d-async is a single-process asynchronous inference worker. It consumes request messages through pluggable Redis pub/sub, Redis sorted-set, or GCP Pub/Sub transports; maps queues/topics to named worker pools; applies merge policies and dispatch gates; and forwards work to `llm-d-router` or another inference gateway over HTTP. Results, retries, cancellation, and durable Redis result delivery use the selected transport.

The service exposes Kubernetes health probes and a controller-runtime metrics endpoint, with optional Kubernetes authentication for metrics. It does not define CRDs or reconcile Kubernetes resources. The Helm chart deploys a namespace-scoped worker and wires broker configuration, optional client TLS material, probes, monitoring resources, and non-root security settings.

## Architectural Analysis

The architecture separates message transport from request processing through a common pipeline abstraction. Queue/topic definitions identify the gateway URL, request path, inference objective, and worker pool. Per-pool merge policies provide fairness and backpressure isolation, while admission or budget gates can use Prometheus-derived capacity signals to prevent asynchronous traffic from consuming capacity needed by online inference. Failed or shed requests are retried until their deadline; durable Redis modes preserve queue state across worker restarts.

The runtime data plane is outbound-only for inference traffic: health and metrics are local HTTP surfaces, while inference requests leave the worker for the configured gateway. The worker can export OpenTelemetry traces and query Prometheus. Transport credentials and TLS files are supplied through Kubernetes Secrets or runtime configuration, so broker and gateway tenancy are deployment concerns rather than application-level identity checks.

The RHOAI/Konflux image is built with `CGO_ENABLED=1` and `GOEXPERIMENT=strictfipsruntime` on a digest-pinned UBI minimal PQC image. The legacy Dockerfile instead builds a static binary into a distroless image. Application TLS uses Go's standard library with a TLS 1.2 minimum when configured, optional CA and client certificates, and a development-only certificate-verification bypass.
