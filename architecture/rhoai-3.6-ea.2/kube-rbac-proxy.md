## Purpose

**Short**: kube-rbac-proxy is a small HTTP reverse proxy that authenticates callers and authorizes each proxied request with Kubernetes RBAC before forwarding it to one upstream service.

**Detailed**: The component is designed primarily as a sidecar in front of an application such as a metrics endpoint. It terminates TLS, identifies callers using bearer tokens, OIDC JWTs, or client certificates, and delegates Kubernetes authorization to TokenReview and SubjectAccessReview APIs. It can also apply static authorization rules and request-derived resource-attribute rewrites.

The proxy exposes a secure listener and forwards authorized traffic to a single configured upstream URL. It supports HTTP/1.1 and HTTP/2, optional h2c upstream connections, client-certificate authentication, upstream CA validation and optional upstream mTLS. RHOAI packages it as a non-root UBI-based container for injection beside platform services.

## Architectural Analysis

kube-rbac-proxy is a deliberately narrow policy enforcement point. Its single-upstream model keeps the trust boundary easy to place beside a workload, while the Kubernetes API remains the source of identity and RBAC decisions. The middleware order is significant: path selection is applied before authentication, then identity headers are optionally added only after authentication, authorization evaluates request-derived attributes, and only an allowed request reaches the reverse proxy.

The component supports both platform-standard TLS termination and certificate rotation through file-backed reloaders. Konflux and Red Hat builds opt into strict FIPS runtime behavior, but the runtime image and final binary should still be checked by the platform check-payload gate. The main configuration risks are deployment-specific: ignored paths bypass policy, h2c disables transport encryption, and broad ClusterRoles or forwarding privileged bearer tokens can defeat the intended isolation.
