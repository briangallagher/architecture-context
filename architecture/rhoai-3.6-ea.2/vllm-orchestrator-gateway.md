## Purpose

**Short**: Provides configurable OpenAI-compatible chat-completions routes that send requests through the FMS Guardrails Orchestrator with fixed detector pipelines.

**Detailed**: The gateway exposes one route per configured entry in `config/config.yaml`, such as `/pii/v1/chat/completions` and `/passthrough/v1/chat/completions`. It accepts standard chat-completions JSON, adds route-selected detector configuration, and forwards the request to the orchestrator's detection endpoint.

For non-streaming responses, detected content can be replaced with the route's configured fallback message. Streaming responses are relayed as server-sent events and are similarly rewritten when detections are present. The gateway is a stateless Rust/Axum process; detector execution and model generation are delegated to the downstream orchestrator and its configured detector/generation services.

## Architectural Analysis

This is a small, configuration-driven HTTP adapter rather than a Kubernetes operator or control-plane component. At startup it loads YAML, normalizes detector server names, validates route references, builds one Axum POST handler per route, and listens on a configurable host and port. The default listener is `0.0.0.0:8090`.

Each request follows the same path: the route determines the detector set, the gateway injects an `input`/`output` detector map, and the request is POSTed to `/api/v2/chat/completions-detection` on the configured orchestrator. The implementation supports both regular JSON responses and SSE streaming. The repository contains no Kubernetes deployment objects, service objects, RBAC, or ingress definitions; those are supplied by the consuming platform delivery configuration.

The gateway has no application-level authentication or authorization policy. It selectively forwards inbound `Authorization` and `X-Forwarded-*` headers to the orchestrator. For orchestrator TLS, it optionally loads a service CA and client certificate/key from fixed paths; hostname verification is explicitly disabled for the `localhost` hostname when the custom CA is present, which should be treated as a deployment-security risk.
