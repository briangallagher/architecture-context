## Purpose

**Short**: Reconciles `OGXServer` and `OGX` custom resources into configured OGX server workloads and manages the OGX operator module lifecycle.

**Detailed**: The primary controller watches namespaced `ogx.io/v1beta1` `OGXServer` resources. It resolves distribution images and base configuration, generates immutable content-hashed ConfigMaps, and renders the server Deployment, Service, storage, networking, disruption, autoscaling, and monitoring resources from the embedded manifests. It also supports adoption of existing resources and optional external access through a Kubernetes Ingress.

The repository also contains the `ogx-module` Go module controller. It watches `OGX` resources and a bounded set of operator/application namespaces, uses dynamic and discovery Kubernetes clients, and deploys or updates the OGX operator resources. Both controllers use controller-runtime, leader election, health probes, and Kubernetes ServiceAccount RBAC.

## Architectural Analysis

This is a control-plane component rather than an application data-plane service. `OGXServer` is the user-facing declarative boundary; reconciliation translates provider, storage, configuration, and network fields into a workload whose generated configuration is versioned by content hash. Retaining two generated ConfigMaps and protecting ConfigMaps referenced by active rollouts reduces the risk of deleting in-flight configuration inputs.

The primary operator is cluster-installed but most server artifacts are namespaced and owned by an individual `OGXServer`. The operator's ClusterRole is broad because it manages workloads and policy objects across namespaces, while the CR itself is namespace-scoped. External access is opt-in and implemented as a plain Kubernetes Ingress with an HTTP backend; TLS termination and authentication are therefore platform/Ingress-controller concerns rather than an application endpoint implemented here.

The admission webhook fails closed for `OGXServer` create and update operations. Webhook serving certificates are mounted from a Secret and can be provisioned by cert-manager. The build uses CGO-enabled Go and a PQC-capable UBI runtime image, and the release manifests include the OpenShift FIPS annotation, but the Go build does not explicitly set `strictfipsruntime`; application TLS uses controller-runtime/OpenShift TLS configuration and defaults where no explicit profile is supplied.
