## Purpose

**Short**: Training Hub provides a registry-driven Python interface for supervised fine-tuning, continual learning, preference/rollout training, embedding fine-tuning, and prompt optimization of language models.

**Detailed**: The package exposes algorithm classes and convenience functions that select a backend, normalize user parameters, and execute training through InstructLab Training, Mini Trainer, Unsloth, ART, or verl. Its core abstraction is the `Algorithm`/`Backend` pair with an `AlgorithmRegistry`, allowing algorithms and backend implementations to be registered and selected at runtime (`src/training_hub/algorithms/__init__.py:6-93`).

Models and tokenizers are loaded from Hugging Face-compatible locations, datasets are prepared through the Transformers/Datasets ecosystem, and checkpoints are written in model-native formats. Optional CUDA, LoRA, GRPO, verl, GEPA, and embedding extras expand the package for accelerator-backed training and external experiment/model services (`pyproject.toml:17-100`). This checkout contains no Kubernetes manifests, service listeners, CRDs, RBAC, or ingress resources; it is consumed as a library or invoked by scripts/notebooks.

## Architectural Analysis

Training Hub is a library-level orchestration layer rather than a control-plane component. The registry decouples public algorithm APIs from execution engines, while adapters translate callbacks and serialized context between Training Hub and distributed/native trainer implementations (`src/training_hub/adapters/*.py`). SFT and OSFT use torchrun-oriented parameters and distributed workers; LoRA uses Transformers/Unsloth and can integrate with MLflow or W&B; verl adds multi-GPU FSDP/vLLM rollout execution and writes reward/checkpoint artifacts (`src/training_hub/algorithms/sft.py:15-104`, `src/training_hub/algorithms/lora.py:76-190`, `src/training_hub/algorithms/lora_grpo_verl.py:747-1004`).

The package has no resident network surface. Network activity is initiated by selected backends and dependencies: model/dataset downloads, LLM calls for GEPA/GRPO, and optional tracking calls. This makes runtime credentials and dependency provenance the principal architecture concerns. `OPENAI_API_KEY` is read and temporarily replaced with a dummy value for local LiteLLM endpoints, then restored (`src/training_hub/algorithms/gepa.py:65-97`, `184-296`). The dependency specification has minimum-version ranges and no repository lock file was found, so reproducibility and hermeticity depend on the consuming build.
