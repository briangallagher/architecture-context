## Purpose

**Short**: Provides an OpenAI-compatible batch API and asynchronous workers that persist batch jobs and dispatch their individual inference requests to llm-d gateways.

**Detailed**: The API server accepts and manages batch jobs and input files through `/v1/batches` and `/v1/files`. It stores job and file metadata in PostgreSQL, uses Redis or Valkey for queue and event exchange, and stores file contents in S3-compatible storage or a filesystem volume.

The batch processor consumes queued jobs, parses input files, creates per-model execution plans, applies global/per-endpoint concurrency and optional AIMD flow control, calls configured llm-d inference gateways, writes output files, and updates job state. The garbage collector removes expired data and can reconcile work left behind after processor failures. The three binaries are deployed independently by the Helm chart.

## Architectural Analysis

This is a stateless API-plus-worker system with shared durable state. The API server separates business traffic from a plain-HTTP observability listener; the processor and garbage collector expose only operational endpoints. A priority queue and database-backed ownership/reconciliation allow multiple processor replicas while the GC is intentionally configured as a singleton by default.

The processor supports synchronous HTTP dispatch and an alternative Redis-backed llm-d-async mode. In synchronous mode it can route by model or by tenant/model key, forwards selected request headers (including the end-user Authorization header when configured), and retries capacity or server failures with backoff. Kubernetes/Kuadrant deployment guides supply the external authentication and model authorization boundary; the application routes themselves do not enforce user authentication.
