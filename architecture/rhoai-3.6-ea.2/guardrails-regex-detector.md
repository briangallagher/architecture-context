## Purpose

**Short**: A lightweight HTTP service that detects predefined or caller-supplied regular-expression patterns in text for integration with the FMS Guardrails Orchestrator.

**Detailed**: The service accepts a list of text contents and detector patterns, evaluates each content against built-in detectors for email addresses, U.S. Social Security numbers, and credit-card-like values, and also supports arbitrary caller-supplied regular expressions. It returns match offsets, matched text, detector type, detector name, and a fixed score of `1.0`.

The application is a single asynchronous Rust/Axum process. It binds one TCP listener, exposes a health endpoint and the detection endpoint, and emits compact request/response tracing through `tower-http` and `tracing-subscriber`. The container image packages the compiled binary in a UBI 9 minimal runtime image and starts it directly.

## Architectural Analysis

This component is a stateless, synchronous-per-request detection service: each request carries the complete input text and detector selection, and the response is computed in memory without a database, queue, Kubernetes API, or outbound service call. The built-in detector names are mapped to fixed regex implementations, while unknown names are interpreted as custom regex expressions. Empty detector lists return HTTP 400; invalid custom expressions are skipped with a warning rather than returned as a request error.

The service has no application-level authentication or TLS configuration in the examined source. It is therefore best treated as an internal service whose transport security and caller authorization must be supplied by its deployment environment or an upstream orchestrator. The Dockerfile installs `compat-openssl11`, but neither the Rust source nor the build invokes an OpenSSL/TLS API, so that package alone is not evidence of FIPS-enabled application transport.
