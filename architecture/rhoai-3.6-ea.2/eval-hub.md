## Purpose

**Short**: EvalHub exposes a REST API that stores and orchestrates LLM evaluations across local processes or Kubernetes Jobs, with optional MLflow, object storage, and MCP integrations.

**Detailed**: The `eval-hub` server accepts evaluation job, provider, collection, result, and log requests. It loads declarative provider and collection definitions, persists state through a SQLite or PostgreSQL storage abstraction, and selects either a local-process runtime or a Kubernetes runtime. The Kubernetes runtime creates namespaced Jobs, ConfigMaps, and Secrets and uses the configured hardware-profile CR for scheduling inputs.

The repository also supplies the runtime sidecar used inside evaluation pods, an init binary that downloads test data and clones Git content, an `evalhub-mcp` server exposing EvalHub capabilities over stdio or HTTP transports, and a `validate_configs` utility. The same Konflux image contains the four deployable binaries; the command is selected by the workload or container override.

## Architectural Analysis

EvalHub is a modular orchestration service rather than a Kubernetes operator. Its central API process separates request context, SQL storage, and runtime execution behind interfaces, allowing the same API to launch local processes in development or namespaced Kubernetes Jobs in RHOAI. The Kubernetes runtime is deliberately resource-oriented and performs explicit cleanup of Jobs, ConfigMaps, and reference Secrets using tenant namespace plus job labels.

The RHOAI deployment boundary is intentionally outside this checkout: there are no static Services, Routes, HTTPRoutes, RBAC, or workload manifests, and the README identifies the TrustyAI Service Operator as the deployment owner. Consequently, ingress hostnames, replicas, probes, RBAC grants, and network policies cannot be established from repository source. The Konflux Dockerfile is the authoritative release build surface; the alternate Containerfile is a local convenience path with `CGO_ENABLED=0` and mutable `latest` base-image semantics.

The strongest isolation path combines platform authentication, trusted identity headers, tenant-aware SQL context, and namespace-scoped Kubernetes operations. The principal architectural risks are the trust placed in forwarded identity headers, the local-mode auth bypass, shared-database isolation being application-enforced rather than database-enforced, and the externally managed RBAC/network policy surface. Metrics are deliberately separated from the API on an unauthenticated cluster-internal listener, which simplifies scraping but requires deployment-level network restriction.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Platform `kube-rbac-proxy` plus required identity headers | Platform and application | Application trusts forwarded headers; direct exposure without the proxy would be unsafe unless another trusted boundary exists. |
| Data storage | SQL storage uses tenant context and separates system versus tenant scope; owner context is also propagated | Application SQL layer | Shared database requires correct query scoping; database-level row security was not found. |
| Network traffic | No NetworkPolicy or AuthorizationPolicy in checkout | External operator/platform | Network isolation and default-deny posture are deployment responsibilities. |
| Compute & resources | Jobs, ConfigMaps, and Secrets are created in the resolved tenant namespace; HardwareProfile controls requested resources | Kubernetes namespace/RBAC and application | Quotas, limits, and cross-tenant scheduling policy are not defined here. |
| Configuration & secrets | Runtime reference Secrets and ConfigMaps are namespaced and labeled by job | Kubernetes and application cleanup | Secret rotation/provisioning is external; shared service credentials can still span tenants if deployed that way. |
| API scoping | `ExecutionContext` supplies tenant/user; handlers call storage `WithTenant`/`WithOwner`; K8s list/delete operations require namespace and label selectors | Application plus Kubernetes | Local mode disables identity-header enforcement for development. |
