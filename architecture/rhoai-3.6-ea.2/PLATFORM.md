## Platform Overview

RHOAI 3.6-ea.2 is an operator-managed AI/ML platform composed of serving, data science, training, model registry, observability, gateway, and evaluation capabilities. The platform operator (`rhods-operator`) provisions in-tree and modular components using ordered reconciliation and readiness gates; specialized operators then reconcile their own CRDs and workloads.

Ingress is a mixed-generation architecture. The platform gateway path uses Gateway API resources, Istio Envoy filters, TLS resources, and `kube-auth-proxy`, while component-specific OpenShift Routes and configurable HTTPRoutes remain present for pipelines, serving, dashboards, and experimental workloads. The shared gateway authentication chain is source-observed as Envoy `ext_authz` calling `kube-auth-proxy` at `/oauth2/auth`, followed by header/token forwarding; backend `kube-rbac-proxy` sidecars and application authorization remain separate enforcement layers. Generic or runtime-configured route joins are retained as unresolved where the source does not fix their parent Gateway.

Security is layered across Kubernetes RBAC, admission webhooks, OAuth/OIDC or bearer-token validation, service-CA/TLS, network policies, and non-root/container build conventions. The structured evidence contains strong observed security signals, but supply-chain, disconnected-deployment, and high-availability enrichment remain unresolved for most components and must not be interpreted as negative findings.

### Ingress Analysis

The strongest end-to-end platform path is the shared Gateway created by `rhods-operator`. Its source template inserts an Envoy HTTP `ext_authz` filter before the router, targeting `https://<kube-auth-proxy>.<gateway-namespace>.svc:<gateway-port>/oauth2/auth`, and permits cookie/authorization/user-agent input plus `x-auth-request-*` and authorization response headers (`rhods-operator/internal/controller/services/gateway/resources/envoyfilter-authn.tmpl.yaml`). The same source renders an OAuth callback HTTPRoute to the auth proxy. The `kube-auth-proxy` source registers the auth-only endpoint under its configured proxy prefix and runs requests through its pre-auth/session chains (`kube-auth-proxy/oauthproxy.go:346-355`), establishing the producer/consumer join. The Lua filter then converts successful auth output into forwarded access-token and authorization headers; this is gateway enforcement, not a backend `kube-rbac-proxy` sidecar.

The AI gateway is a separate composition. Its ODH overlay renders an EnvoyFilter and DestinationRule for the Praxis/payload-processing data plane; the payload-processing service registers Envoy's `ExternalProcessor` gRPC service on its configured port (`ai-gateway-payload-processing/cmd/runner.go:271-292`). This supports request/response transformation, provider resolution, and metering, but the source does not establish a universal authentication policy for every tenant route. Such joins remain candidate/configuration-dependent.

KServe, DSP, model-registry, Kubeflow, workbench, Ray, and llm-d paths coexist with the shared Gateway migration. Their inventories identify HTTPRoutes, OpenShift Routes, Ingresses, and runtime-selected surfaces, but generic or missing `parentRefs` and generated ownership prevent a single universal route map. Missing dependency edges are therefore unresolved integration evidence, not evidence of absent connectivity.

## Platform Architectural Analysis

RHOAI uses a layered operator architecture: a platform meta-operator coordinates modules, modules vendor or render subordinate manifests, and workload controllers reconcile capability CRDs. This creates a coherent lifecycle model and supports OCP/xKS variants, but it also concentrates permissions and lifecycle coupling in platform/module operators. The dependency tree understates runtime integration because generated Gateway, Route, Service-selector, Envoy, and configuration relationships are not uniformly represented as code-import edges.

Ingress is undergoing a deliberate transition from component-owned OpenShift Routes to shared Gateway API/Envoy infrastructure. The shared auth path is source-resolved for `rhods-operator -> Envoy ext_authz -> kube-auth-proxy`; AI gateway `ext_proc` is source-resolved as a processing path. Generic HTTPRoute parent references, runtime-generated gateway ownership, and tenant policy attachment remain candidate or unresolved. These states matter to feature assessment: they must not be converted into unsupported/absent conclusions.

The platform has several distinct serving paths: classic KServe InferenceService, KServe LLMInferenceService with EPP/InferencePool, external-provider/MaaS passthrough through AI gateway payload processing, and multi-model or provider-routing paths. They share Gateway API and model-serving infrastructure in places, but their routing and provider roles are not interchangeable. Serving-related evidence also shows multiple autoscaling and distributed-inference options, with exact activation controlled by profiles and overlays.
