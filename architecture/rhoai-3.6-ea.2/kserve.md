## Purpose

**Short**: KServe manages Kubernetes model-serving resources and turns inference, LLM inference, and local-model cache declarations into serving workloads and network endpoints.

**Detailed**: The repository contains several controller-runtime binaries: the primary InferenceService controller, InferenceGraph and router support, LLMInferenceService controllers, a KServe module controller, and local-model cache/node controllers. These reconcile namespaced serving resources and a cluster-scoped `Kserve` platform configuration into Deployments, Services, autoscalers, routes, model runtimes, credentials, and status conditions.

KServe also packages Python storage and model-server implementations for frameworks such as vLLM, Hugging Face, MLServer, Triton, TensorFlow, PyTorch, XGBoost, scikit-learn, LightGBM, Paddle, PMML, and AutoGluon. The resulting architecture separates control-plane reconciliation from data-plane model servers while supporting serverless/Knative, standard Kubernetes, Gateway API, and OpenShift Route integration.

## Architectural Analysis

KServe is a broad control plane rather than a single service. The primary controller, LLM controller, module controller, and local-model controllers each have distinct deployment and RBAC surfaces, but coordinate through KServe CRs and generated Kubernetes workloads. This allows ordinary inference and newer LLM inference flows to share model-runtime abstractions while retaining specialized scheduling, gateway, and cache behavior.

The RHOAI branch adds a `components.platform.opendatahub.io/v1alpha1 Kserve` configuration resource and prefetched runtime manifests. The module controller uses that configuration to install or reconcile CRDs, runtimes, monitoring, network policy, certificates, and related platform integrations. Inference traffic is therefore dynamically materialized from CRs; the analyzer found no static ingress route, while source and API types show support for HTTPRoute and OpenShift Route modes.

The main risks are the breadth of cluster privileges (including RBAC bind/escalate in the module controller), dynamically composed routes and workload templates, and the coexistence of multiple ingress/deployment modes. Analyzer coverage is sufficient for baseline inventory but marks source behavior, Kustomize replacements, Python call graphs, and dynamic routes as partial; those limits matter when interpreting generated runtime names and endpoint exposure.
