## Purpose

**Short**: Kubeflow Pipelines services compile, submit, execute, persist, visualize, and expose machine-learning workflows on Kubernetes.

**Detailed**: The component combines a Go API server, v2 compiler/driver/launcher, persistence and scheduled-workflow controllers, cache server, viewer and visualization services, and a Python SDK. Pipelines are represented by namespaced `Pipeline` and `PipelineVersion` custom resources and are executed through Argo Workflows.

The deployment includes the pipeline API/UI, metadata services, cache, MySQL or PostgreSQL-backed persistence, SeaweedFS object storage, and optional cloud-provider components. The API exposes REST and gRPC interfaces; the API service also hosts validating and mutating admission webhooks for `PipelineVersion` resources.

## Architectural Analysis

This is a distributed control plane rather than a single operator binary. The API server is the front door for pipeline CRUD, uploads, runs, artifacts, and recurring runs. The driver and launcher translate pipeline specifications into Kubernetes/Argo execution, while the scheduled-workflow controller and persistence agent reconcile workflow lifecycle and database state. The viewer controller and visualization server provide execution inspection.

The deployment is namespace-oriented: core pipeline CRDs are namespaced, service-account tokens are mounted for Kubernetes API access, and configuration commonly derives the active namespace from pod metadata. Shared MySQL/PostgreSQL, metadata, cache, and object-storage services form a common data plane, so tenant isolation depends on namespace/RBAC configuration and the API’s multi-user authorization mode.

The analyzer reports complete manifest inventory but only partial semantic coverage for dynamic Go routes, Python imports/call graphs, and platform aliases. Accordingly, unresolved authentication, TLS, dynamic route, and RBAC details are marked unknown below rather than inferred.
