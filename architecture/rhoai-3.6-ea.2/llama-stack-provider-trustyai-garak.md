## Purpose

**Short**: Provides an eval-hub `FrameworkAdapter` that runs NVIDIA Garak red-team scans against LLM endpoints and returns structured vulnerability results.

**Detailed**: The package integrates Garak with the RHOAI eval-hub evaluation platform. It accepts an eval-hub `JobSpec`, resolves a named benchmark profile and model configuration, runs Garak probes, parses JSONL results, calculates attack and vulnerability metrics, and reports results and generated artifacts through eval-hub callbacks. Profiles cover OWASP LLM Top 10, AVID, quality, CWE, and other security-oriented scans.

The default `simple` mode runs Garak as a subprocess in the eval-hub-created Kubernetes Job. The `kfp` mode submits a six-step Kubeflow Pipeline (`validate`, taxonomy resolution, SDG, prompt preparation, scan, and output writing), polls the KFP run, and exchanges reports through an S3-compatible RHOAI Data Connection. The `intents` benchmark adds taxonomy-driven synthetic data generation and TAPIntent scanning and is designed for the KFP workflow.

## Architectural Analysis

This is an execution adapter and library, not a Kubernetes controller or independently exposed server. Its deployment topology is supplied by eval-hub: the adapter consumes a mounted job specification and platform callbacks, while the KFP path creates the actual pipeline pods and uses Kubernetes APIs and credentials available in the runtime environment. Consequently, the analyzer's zero-workload/zero-service result describes this repository's source tree, not the workloads created by eval-hub or KFP at runtime.

The design cleanly separates benchmark/configuration resolution, Garak command construction and subprocess lifecycle, result parsing, and eval-hub/KFP I/O. The two modes share core pipeline steps and result processing. The KFP mode introduces a remote control-plane dependency and a shared object-store data plane: the adapter submits and polls a run, then downloads results from a prefix derived from the job ID. KFP component images are resolved from explicit configuration, environment, a ConfigMap, or a digest-pinned default.

Security-sensitive values are resolved from mounted Kubernetes secrets, eval-hub secret helpers, and environment variables; generated `config.json` content is redacted before upload. TLS verification is enabled by default for the general HTTP client and KFP client, with configurable CA paths, but both KFP and Kubernetes-secret proxy code have explicit fallback paths that can disable verification or use plain HTTP endpoints when configuration requests it. Deployment manifests, RBAC, NetworkPolicies, and resource limits are owned by the consuming eval-hub/KFP deployment and are not present here.
