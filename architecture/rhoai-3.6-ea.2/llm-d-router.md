## Purpose

**Short**: Provides intelligent LLM inference routing through an Envoy external processor, Kubernetes Gateway API integration, request-management APIs, and an optional prefill/decode coordination sidecar.

**Detailed**: The llm-d Router combines an Endpoint Picker (EPP) with a proxy data plane. The EPP receives Envoy external-processing requests over gRPC and selects model-server endpoints using load, KV-cache locality, prioritization, flow-control, and configurable scoring plugins. Gateway mode connects an `HTTPRoute` to an `InferencePool`; standalone mode can deploy Envoy or AgentGateway beside the EPP or as a separately scalable proxy service.

The repository also contains controllers for `InferencePool`, `InferenceObjective`, `InferenceModelRewrite`, and Pods, plus a coordinator for multi-stage inference workflows and an optional async-broker API. The disaggregation sidecar coordinates encode, prefill, and decode workers and transfers KV-cache or embedding state. The release checkout supplies Helm charts and Kustomize manifests for these runtime variants.

## Architectural Analysis

The architecture separates request ingress from scheduling intelligence. Envoy or another Gateway API-compatible proxy owns the client-facing data plane, while the EPP implements the ext-proc control decision and maintains model-endpoint state from Kubernetes watches. This permits the same scheduling engine to operate with a self-managed proxy or a platform-managed Gateway, but makes correct `InferencePool`, `HTTPRoute`, service, and proxy protocol configuration a deployment responsibility.

The release has three principal Go executables: EPP, coordinator, and `pd-sidecar`. EPP is the primary low-latency routing service; coordinator is a workflow-oriented component with rendering, encode/prefill/decode, tracing, and optional async-broker steps; the sidecar is colocated with a decode worker for disaggregated inference. Redis, ZeroMQ KV-event transport, Kubernetes APIs, and optional external model/rendering services create a distributed runtime with several independently configurable failure and timeout domains.

The Konflux images explicitly enable dynamic CGO and `strictfipsruntime`, and use digest-pinned UBI PQC runtime images. The ordinary upstream Dockerfiles intentionally build static binaries, so FIPS posture depends on selecting the Konflux image path. Application gRPC TLS is optional and application authentication interceptors are not configured; network placement and the surrounding Gateway/RBAC policy therefore remain important security boundaries.
