## Purpose

**Short**: TrustyAI provides fairness, drift, and explainability capabilities as a Java library and a deployable Quarkus REST service.

**Detailed**: The repository combines the `explainability-core`, Arrow interoperability, connector, and service modules. The service exposes TrustyAI functionality for model explanations and fairness/drift analysis and includes integrations for KServe/ModelMesh inference services. The RHOAI profile enables fairness and drift endpoints while disabling local and global explainer endpoints in the checked-in application configuration.

The Kubernetes deployment runs one `trustyai-service` replica on port 8080, stores service data under `/inputs` on a 1 GiB ReadWriteOnce PVC, and publishes an OpenShift Route. An init container uses the OpenShift CLI and the pod namespace to update a `model-serving-config` ConfigMap with the service's KServe v2 payload-processor URL.

## Architectural Analysis

TrustyAI is a modular Java 17 application whose reusable analysis algorithms are separated from the Quarkus HTTP service. The service selects storage implementations through configuration, supporting PVC/CSV operation and database-backed operation (MariaDB or MySQL, with H2 used for tests); source code also contains a MinIO storage implementation. This makes the runtime adaptable, but the deployment manifest shown here configures the PVC/CSV path and does not define database or object-store credentials.

The release deployment is deliberately simple—one application container, one PVC, a ClusterIP service, and an OpenShift Route—but the init-container ConfigMap mutation gives the workload a cluster-wide ConfigMap permission. The Route has no TLS stanza and the service's configured certificate files are not mounted by the manifest, so transport protection and external authentication appear to be supplied by the surrounding platform or are absent in this artifact. RHOAI-specific endpoint flags also make the deployed surface narrower than the default and ODH profiles.
