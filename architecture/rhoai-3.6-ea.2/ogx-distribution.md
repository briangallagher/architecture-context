## Purpose

**Short**: Packages the Open Data Hub OGX server, its Python dependencies, model artifacts, runtime configuration, and secret-loading entrypoint into a RHOAI distribution image.

**Detailed**: The image provides a configurable OGX API server for responses, messages, batches, inference, tool runtime, vector I/O, files, and file processing. Built-in providers handle local files and reference/batch behavior, while environment variables selectively enable remote inference, search, object storage, vector databases, and embedding services.

The distribution uses PostgreSQL for key-value and SQL persistence, ships pre-fetched model/data artifacts from a scanned modelcar image, and runs as an unprivileged application container. The image is intended to be deployed and exposed by platform integration such as the OGX operator; this repository supplies the image and a ServiceMonitor selector rather than Kubernetes workloads or ingress resources.

## Architectural Analysis

ogx-distribution is a packaging and runtime-configuration boundary around the upstream OGX Python service. The generated `config.yaml` composes multiple API surfaces over a common server on TCP 8321, with provider implementations selected through environment-variable presence. This makes the same image usable with local storage, PostgreSQL, remote model endpoints, S3-compatible storage, Milvus, Qdrant, and provider-specific cloud APIs.

The build separates release/container concerns from runtime concerns. Konflux builds install a hashed, RHOAI-indexed Python lockfile offline after sourcing cachi2 metadata, run RPM database and self-tests, and copy model/data content from a pre-published modelcar. The ordinary Containerfile uses a midstream Python base and verifies hashes while installing the general lockfile. Both paths copy the generated configuration and a shell entrypoint that resolves `_FILE` secret variants before starting OGX.

Authentication is application-configured OAuth2/JWT validation using an issuer, audience, JWKS URI, optional CA file, and TLS verification enabled by default. Resource policy permits reads of unowned resources, permits authenticated creation, and limits update/delete to owners. Tenant isolation is therefore primarily an application-level concern; the distribution contains no Kubernetes RBAC or network-policy enforcement and relies on the surrounding platform and OGX implementation for request identity propagation.
