## Purpose

**Short**: Manages ModelRegistry, Catalog, and AIHub custom resources and the deployments, databases, authentication proxies, RBAC, routes, and Gateway API resources that implement them.

**Detailed**: The operator runs controller-runtime managers for ModelRegistry, Catalog, and AIHub resources. A ModelRegistry reconciler creates a REST model-registry deployment, an optional PostgreSQL deployment and credentials, service accounts, namespace-scoped RBAC, NetworkPolicies, Services, and either OpenShift Routes or Gateway API HTTPRoutes. The Catalog reconciler creates a catalog API backed by PostgreSQL and ConfigMap-provided catalog sources. The AIHub controller manages cluster-scoped AIHub configuration and catalog resources.

The operator also serves health/readiness endpoints, an authenticated metrics endpoint, and admission/conversion webhooks. ModelRegistry v1alpha1 is converted to the v1beta1 hub version; mutating defaulting migrates legacy OAuth proxy configuration to kube-rbac-proxy, and validating admission enforces namespace and database requirements. On OpenShift, TLS settings are derived from the cluster TLS profile and serving certificates are supplied through platform annotations or referenced Secrets.

## Architectural Analysis

This is a multi-controller operator with a shared Go entrypoint and three deployment modes selected by Cobra subcommands. The control plane is deliberately namespace-bounded for managed workloads: ModelRegistry and Catalog objects are namespaced, the configured registries namespace is enforced by validation, and controller caches use operator-created labels or explicit namespace scoping. AIHub is cluster-scoped and acts as a higher-level composition point for Catalog resources.

The deployment model supports both RHOAI 3.x Gateway API ingress and OpenShift Route compatibility. Gateway mode creates HTTPRoutes in a configurable namespace referencing a configurable Gateway and uses kube-rbac-proxy as the authenticated backend. Route mode creates HTTP and re-encrypt HTTPS Routes. Database credentials, TLS keys, external database certificates, and catalog API keys are referenced from Kubernetes Secrets rather than embedded in the operator image. The Konflux build is FIPS-oriented and digest-pinned, while the local Dockerfile remains a non-FIPS CGO-disabled build path; the branch has Go module locking but no RPM/Hermeto lock artifacts.

The validating handler checks that a ModelRegistry is in the configured registries namespace and has a supported database configuration. The mutating handler defaults kube-rbac-proxy and route settings, creates default TLS Secret references, and migrates legacy OAuth proxy settings. Webhook behavior is enabled by default in the operator process but its deployment manifests are composed by the ODH overlay.
