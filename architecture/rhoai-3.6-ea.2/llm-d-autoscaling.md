## Purpose

**Short**: Workload Variant Autoscaler (WVA) watches inference workloads and autoscaling resources, queries Prometheus, and adjusts deployment-scale targets for LLM inference.

**Detailed**: The component is a controller-runtime manager deployed as `controller-manager`. It discovers workload variants through ConfigMaps, HPAs, InferencePool resources, and optionally KEDA ScaledObjects, then combines runtime metrics and configuration to drive autoscaling decisions. It can operate cluster-wide or be restricted to a configured namespace.

The manager also exposes health probes and a protected metrics endpoint. It integrates with the Kubernetes API, Prometheus, KEDA, the Gateway API Inference Extension, LeaderWorkerSet resources, and Prometheus Operator ServiceMonitor resources. Leader election ensures a single active controller instance when enabled by the deployment.

## Architectural Analysis

WVA is a control-plane autoscaler rather than a serving data plane. Its central loop is event-driven: controller-runtime watches Kubernetes objects, while a Prometheus client supplies the measurements used by the autoscaling and optimization logic. The reconciler set covers configuration, HPA state, InferencePool state, and optional KEDA discovery; direct actuator code updates Kubernetes scale subresources.

The design supports both platform-wide operation and namespace-scoped instances. In the default mode, ConfigMaps are cached across namespaces but filtered to WVA-labeled objects; a `watch-namespace` setting constrains the cache to one namespace. The repository’s multi-controller end-to-end tests demonstrate independent namespace-scoped instances and namespace-labeled Prometheus metrics, but the primary RBAC manifest grants cluster-wide read/update permissions, so deployment configuration remains the effective isolation boundary.

Security is layered: health probes are intentionally unauthenticated, metrics use controller-runtime TokenReview/SubjectAccessReview authorization, Kubernetes API calls use the controller ServiceAccount, and Prometheus transport supports CA and client certificates. Prometheus TLS enforces TLS 1.2 by default, but an explicit development/testing setting can disable certificate verification; the container build itself uses CGO-disabled static Go and a distroless static image, so it does not provide the dynamic-OpenSSL build posture expected by a FIPS check-payload gate.
