## Purpose

**Short**: rhoai-mcp is a Model Context Protocol server that lets AI agents inspect and manage Red Hat OpenShift AI resources through authenticated tools.

**Detailed**: The server exposes FastMCP tools over stdio, SSE, or streamable HTTP. Its domain and composite plugins cover projects, notebooks/workbenches, model serving, model registries and catalogs, data connections, pipelines, storage, and Kubeflow training workflows. The server uses the Kubernetes Python client for cluster resources and HTTPX for Model Registry and Model Catalog REST APIs.

In the RHOAI deployment, a single non-root Deployment runs in the `rhoai-mcp` namespace and is exposed by a ClusterIP Service on port 8000. The OpenShift overlays add an edge-terminated Route; the OIDC variant validates caller identity and either forwards the caller token or impersonates the caller for Kubernetes authorization. An alternate MCPServer overlay delegates Deployment and Service lifecycle to the MCP Lifecycle Operator.

## Architectural Analysis

rhoai-mcp is a plugin-oriented control-plane gateway rather than a model-serving data plane. FastMCP dispatches agent tool calls to domain clients, which use Kubernetes API CRUD/watch operations or HTTP REST calls to platform services. The shared Kubernetes client supports in-cluster ServiceAccount, kubeconfig, and explicit bearer-token authentication; OIDC mode replaces the shared identity for resource operations with a per-request user token or validated impersonation headers.

The base deployment is deliberately constrained with non-root execution, RuntimeDefault seccomp, dropped capabilities, no privilege escalation, read-only root filesystem, bounded CPU/memory, and health probes. The OpenShift OIDC configuration is the strongest multi-user posture: TokenReview or JWT validation is combined with SubjectAccessReview-driven tool filtering and user-scoped Kubernetes calls. The default non-OIDC ClusterRole remains highly privileged and cluster-scoped, so it should be limited to trusted deployments.

The Konflux build extends the AIPCC CPU image by installing the Python package from source. The image is digest-pinned, but the repository does not provide RPM or artifact lock files and the Konflux Dockerfile does not show Hermeto/cachi2 prefetch. The application uses `cryptography`, PyJWT, HMAC-SHA256 workflow tokens, and HTTPX certificate verification; Model Registry TLS verification can be explicitly disabled, which is a documented production risk.
