## Purpose

**Short**: Extracts, enriches, validates, and catalogs model and MCP-server metadata from Hugging Face collections, OCI images, and checked-in YAML data.

**Detailed**: `model-extractor` is the primary batch pipeline. It loads model indexes, optionally discovers Red Hat AI collections from Hugging Face, processes OCI model images concurrently, extracts model cards from image layers, enriches metadata from Hugging Face and vLLM configuration, and writes per-model metadata plus aggregate catalogs. Static catalog inputs are merged with extracted results.

The repository also builds `metadata-report`, a separate CLI that reads an existing catalog and extraction output to generate human- and machine-readable completeness reports. The Konflux image is a non-root, data-distribution container: it copies pre-generated YAML catalogs into `/app/data`, mounts that directory, and stays alive with `sleep infinity`; it does not expose an application server or Kubernetes API.

## Architectural Analysis

This is a source-processing pipeline rather than a continuously running platform service. `model-extractor` coordinates domain packages for configuration, Hugging Face access, registry access, metadata parsing, enrichment, and catalog generation. Per-model work is bounded by a configurable semaphore/concurrency limit (default five), while registry access uses the containers/image library to inspect OCI manifests and layers. The resulting catalogs are consumed as files by downstream platform components.

The release-oriented `Dockerfile.konflux` is preferred for distribution. It uses a digest-pinned `ubi-minimal-pqc` base and contains only catalog YAML data, while the general Dockerfile is a separate catalog/benchmark image based on `ubi9-micro`. Neither Dockerfile builds or copies the Go executables; executable builds are defined by the Makefile. This split means the published Konflux artifact is principally a catalog payload, not the extraction runtime.

The main operational risks are external-source availability and credential scope: collection/model reads depend on Hugging Face, OCI metadata depends on registries, and optional agent metadata uses GitHub. Requests have 30-second client timeouts, and Bearer tokens are read from environment variables when present. Catalog generation is file-based and has no service-level authentication, RBAC, tenant boundary, or network policy of its own.
