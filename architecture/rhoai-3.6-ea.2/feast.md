## Purpose

**Short**: Feast provides feature-store APIs and a Kubernetes operator that deploys and manages FeatureStore instances for machine-learning workloads.

**Detailed**: The Python SDK and feature server provide registry, online/offline feature retrieval, materialization, push, monitoring, lineage, UI, and vector-store capabilities. The Go services expose the embedded serving and health/metrics surfaces, while the Python server exposes the broader REST, gRPC, WebSocket, and UI API surface on port 6566.

The Feast operator watches namespaced `FeatureStore` resources and reconciles feature-store services, deployments, jobs, PVCs, service accounts, RBAC, routes, monitoring resources, and supporting configuration. It also integrates with Kubernetes, OpenShift Routes, Kubeflow Notebooks, MLflow, Prometheus, and configurable data stores such as PostgreSQL, Redis/Valkey, S3/GCS, and Ray.

## Architectural Analysis

Feast is a split control/data-plane component. The operator is a cluster-installed control plane with a namespaced `FeatureStore` API; each custom resource selects the services and storage backends to instantiate. The feature server is a Python application with embedded Go serving functionality, so the deployed surface combines controller-runtime behavior with a large application API rather than a narrowly scoped operator-only interface.

The RHOAI overlay deploys the operator into `redhat-ods-applications` and parameterizes related images and the external OIDC issuer through a generated ConfigMap. Operator-created workloads are namespace-oriented, but the controller holds broad cluster permissions and can create cluster-scoped RBAC bindings. This makes Kubernetes RBAC and the operator's generated access policy central to tenant isolation.
